ย้อนกลับไปที่เคสทีม support ที่ ticket ค้างเยอะขึ้นจากโมดูลแรกของ track นี้ — ตอนนั้นเราเห็นว่ามันมี feedback loop ซ่อนอยู่ ตอนนี้เรามีคำศัพท์ครบพอจะวาดมันเป็น causal loop diagram ได้แล้ว และจะเห็นตัวการตัวจริงที่ทำให้ปัญหานั้นแก้ยาก — ไม่ใช่แค่ "มี feedback loop" เฉยๆ แต่เป็นเพราะ **loop นั้นมี delay ซ่อนอยู่**

โครงสร้างนี้เหมือน balancing loop ของ autoscaling ในหัวข้อแรกของโมดูลนี้เป๊ะทุกประการ — เป็น B loop (มีลิงก์ลบ 1 เส้น) ควรจะดึง ticket backlog กลับเข้าสู่ระดับที่รับไหวได้ แต่ความต่างเดียวที่ทำให้พฤติกรรมจริงต่างไปมหาศาลคือ **delay บนเส้นกลาง** — ระหว่างที่รอ ผู้จัดการเห็น backlog ยังสูงอยู่ (เพราะผลของการจ้างยังไม่ทันออกฤทธิ์) จึงตัดสินใจจ้างเพิ่มอีกรอบ ซ้อนกับรอบแรกที่ยังไม่ทันเห็นผล

## กฎทั่วไป: Delay ทำอะไรกับแต่ละชนิดของ Loop

**Delay ใน Balancing Loop → เสี่ยง oscillation/overshoot** — เพราะระบบ "แก้" ซ้ำก่อนที่จะเห็นผลของการแก้ครั้งก่อนครบ ยิ่ง delay นาน ยิ่งเสี่ยงแก้เกินจำเป็นซ้ำแล้วซ้ำเล่า (พฤติกรรมแบบนี้จะเห็นเป็นกราฟจริงในหัวข้อ Oscillation ของโมดูลถัดไป)

**Delay ใน Reinforcing Loop → บดบังความเร็วที่แท้จริงของการเติบโต** — ปัญหาคือคนละแบบกับ B loop เพราะไม่มี "แก้เกิน" แต่เป็นการ "รู้ตัวช้าเกินไป" เช่น cache hit rate ที่ค่อยๆ ลดลงจาก resource ที่รั่วสะสม กว่า dashboard จะแสดงผลกระทบชัดพอให้ทีมสังเกตเห็น ปัญหาอาจสะสมมาหลายสัปดาห์แล้ว (เหมือนกบต้มที่ไม่รู้ตัวว่าน้ำร้อนขึ้นทีละนิด) พอรู้ตัวอีกที stock (เช่น memory leak, error rate) อาจโตไปไกลเกินจะแก้ง่ายๆ แล้ว

| ชนิด Loop | ผลของ Delay | ตัวอย่าง |
|---|---|---|
| Balancing (B) | Oscillation — แกว่งเกินเป้าไปมา | Hiring ที่จ้างซ้ำเพราะรอ onboarding, autoscaling ที่ over-provision |
| Reinforcing (R) | รู้ปัญหาช้า — สะสมไปไกลก่อนสังเกตเห็น | Memory leak ที่ dashboard sampling ทุก 15 นาที, viral growth ที่วัด conversion หลัง 30 วัน |

## หลักปฏิบัติที่นำไปใช้ได้ทันที

ก่อนแก้ปัญหาที่ดูเหมือนเป็นวงป้อนกลับ ให้ถามสองคำถามเสมอ: **"loop นี้เป็น R หรือ B"** (จากโมดูลนี้) และ **"มี delay อยู่บนเส้นไหนบ้าง กี่นาน"** — คำตอบของสองคำถามนี้ร่วมกันบอกได้เกือบทั้งหมดว่าควรรอสักพักก่อนแก้ซ้ำ (ถ้าเป็น B loop ที่มี delay) หรือควรรีบขยับก่อนที่จะสายเกินไป (ถ้าเป็น R loop ที่มี delay บดบังความเร็วจริง)

โมดูลนี้ให้คำศัพท์ครบแล้ว: stock, flow, delay จากโมดูลก่อน และตอนนี้ B loop, R loop, การอ่าน causal loop diagram จากโมดูลนี้ — โมดูลถัดไป **Behavior Patterns** จะเอาทั้งหมดนี้มาประกอบกันเป็น "กราฟพฤติกรรม" 4 แบบที่พบซ้ำๆ ในระบบทุกประเภท: exponential growth, goal-seeking, oscillation, และ overshoot and collapse — เป็นการเชื่อมจาก "โครงสร้าง" (structure) ที่เรียนมาทั้งหมด ไปสู่ "พฤติกรรมที่มองเห็นได้จริง" (behavior) ตามหลักการที่วางไว้ตั้งแต่โมดูลแรก
