Startup แอปหนึ่งปล่อยฟีเจอร์ "เชิญเพื่อน" แล้วยอดผู้ใช้พุ่งแบบทวีคูณ 3 เดือนแรกไม่มีอะไรหยุดได้เลย ทีมเริ่มเชื่อว่ากราฟนี้จะพุ่งต่อไปเรื่อยๆ แต่พอเข้าเดือนที่ 4 กราฟที่เคยชันกลับแบนราบกะทันหัน ทีมงงว่าฟีเจอร์เสียหรือเปล่า — ความจริงคือไม่มีอะไรเสีย มีแค่ **loop คนละตัวเข้ามาควบคุมพฤติกรรมแทน**: ช่วงแรก reinforcing loop (ยิ่งมีคนใช้ ยิ่งมีคนเชิญเพิ่ม) เป็นตัวขับเคลื่อนหลัก แต่พอ server เริ่มใกล้ capacity balancing loop (ยิ่ง server ช้า ยิ่งมีคนเลิกใช้ก่อนจะเชิญต่อ) ก็เข้ามาคานจนพฤติกรรมเปลี่ยนหน้ามือเป็นหลังมือ

## ระบบจริงแทบไม่เคยมี Loop เดียว — มันมีหลาย Loop ทำงานพร้อมกันเสมอ

สามบทที่ผ่านมาสอน balancing loop กับ reinforcing loop แยกกันทีละแบบ เพื่อให้เห็นกลไกแต่ละชนิดชัดๆ แต่ระบบจริงแทบไม่เคยมีแค่ loop เดียวโดดๆ — มันมักมีทั้ง R loop และ B loop ทำงาน**พร้อมกัน**ตลอดเวลา เพียงแต่ ณ ช่วงเวลาหนึ่งๆ loop ตัวใดตัวหนึ่งจะ "แรงกว่า" อีกตัวมากจนดูเหมือนเป็นตัวเดียวที่กำหนดพฤติกรรม แนวคิดที่ว่า loop ไหนกำลังเป็นตัวควบคุมพฤติกรรมระบบ ณ ช่วงเวลานั้น เรียกว่า <mark class="hl-term">**Loop Dominance**</mark>

## สัญญาณที่บอกว่า Loop กำลังจะเปลี่ยนมือ

การเปลี่ยน dominance มักไม่ได้เกิดแบบฉับพลันไม่มีปี่มีขลุ่ย — มันมีสัญญาณเตือนล่วงหน้าเสมอถ้ารู้จะมองตรงไหน:

| สัญญาณ | ความหมาย |
|---|---|
| กราฟที่เคยชันเริ่ม "โค้ง" ผิดปกติ ก่อนจะแบนจริง | loop ที่กำลังจะเข้ามาครอบงำเริ่มสะสมแรงพอจะเห็นผลกระทบเล็กๆ แล้ว แม้ยังไม่ชนะ loop เดิม |
| ตัวแปรที่เคย "คงที่ไม่สนใจ" เริ่มขยับ | เช่น latency ที่เคยนิ่งอยู่ 50ms เริ่มขยับเป็น 80ms, 120ms — เป็นสัญญาณว่า loop ที่เกี่ยวกับ latency กำลังเริ่มมีน้ำหนัก |
| คนในทีมเริ่มบ่นเรื่องที่ไม่เคยบ่นมาก่อน | สัญญาณเชิงคุณภาพ (qualitative) มักมาก่อนตัวเลขเชิงปริมาณ (quantitative) เสมอ |

<mark class="hl-warning">ทีมที่รอจนกราฟพลิกชัดเจนแล้วค่อยตอบสนอง มักสายเกินไปแล้ว เพราะ delay ระหว่าง loop เริ่มมีน้ำหนักกับพฤติกรรมของระบบที่เปลี่ยนชัดเจน อาจกินเวลาหลายสัปดาห์หรือหลายเดือน — เรื่องนี้เชื่อมโยงตรงกับหัวข้อ delay ที่เพิ่งเรียนไป</mark>

## ทำไมการทำนาย Loop Dominance ล่วงหน้าถึงยากเป็นพิเศษ

ความยากอยู่ที่ loop ที่กำลังจะเข้ามาครอบงำ มักเป็น loop ที่ "เล็กเกินกว่าจะสนใจ" ในช่วงที่ loop เดิมยังแรงอยู่ — ทีมส่วนใหญ่จัดสรรความสนใจตามสัดส่วนของผลกระทบปัจจุบัน ไม่ใช่ตามศักยภาพในอนาคต การจะจับสัญญาณ dominance shift ให้ทันจึงต้องอาศัยการตั้งคำถามเชิงรุกว่า "มี loop ไหนบ้างในระบบนี้ที่ตอนนี้ยังเบา แต่จะหนักขึ้นถ้าเงื่อนไขเปลี่ยน" แทนที่จะมองแค่ loop ที่กำลังส่งผลชัดเจนที่สุด ณ ขณะนี้

โมดูลถัดไปจะพาไปดู **Behavior Patterns** — กราฟรูปทรงต่างๆ ที่เกิดจากโครงสร้าง loop แบบต่างๆ ที่เรียนมาทั้งหมด รวมถึงกราฟรูปทรงที่เกิดขึ้นตรงๆ จากการที่ loop สองตัวแย่งกันครอบงำแบบที่เพิ่งเห็นในบทนี้
