สองหัวข้อก่อนหน้าเจอ loop แบบง่ายๆ ที่มีวงเดียว บอกได้ทันทีว่าเป็น R หรือ B โดยไม่ต้องคิดมาก แต่ระบบจริงแทบไม่เคยมีแค่ loop เดียว — มันมีหลาย loop ซ้อนทับกัน แชร์ node ร่วมกัน บาง loop ดึงไปทาง balance บาง loop ดันไปทาง reinforce พร้อมๆ กัน หัวข้อนี้จะสอนวิธี**อ่าน**ไดอะแกรมแบบนั้นอย่างเป็นระบบ ไม่ใช่เดาสุ่ม

## กฎการนับที่ใช้ได้เสมอ

วิธีอ่านมีขั้นตอนตายตัวแค่ 3 ขั้น ใช้ได้กับทุก loop ไม่ว่าจะซับซ้อนแค่ไหน:

1. **เลือก loop หนึ่งวง** — เดินตามลูกศรจนกลับมาที่จุดเริ่มต้นพอดี (closed path)
2. **นับจำนวนลิงก์ "−" ตลอดทางที่เดิน** — นับเฉพาะ loop นี้วงเดียว ไม่เกี่ยวกับ loop อื่นที่อยู่ในไดอะแกรมเดียวกัน
3. **ตัดสิน**: นับได้เลขคู่ (รวมศูนย์) = **Reinforcing (R)**, นับได้เลขคี่ = **Balancing (B)**

จุดที่คนอ่านผิดบ่อยที่สุดคือขั้นที่ 2 — เผลอนับลิงก์ที่ไม่ได้อยู่ใน loop ที่กำลังพิจารณาปนเข้าไปด้วย เพราะไดอะแกรมจริงมักมี node ที่ share กันระหว่างหลาย loop ต้องแยกให้ชัดว่ากำลัง "เดิน" อยู่ในวงไหน

ลองไล่ตามขั้นตอน 3 ข้อกับไดอะแกรมนี้:

**Loop บน (สามเหลี่ยม incidents → load → fatigue → incidents):** ลิงก์ทั้งสามเป็น "+" หมด → นับลิงก์ลบได้ 0 (เลขคู่) → **R loop** — incident เยอะ ทำให้ on-call load หนัก ทำให้ทีมเหนื่อยล้า (fatigue) ทำให้พลาด/ตอบสนองช้าลง ซึ่งทำให้เกิด incident เพิ่มอีก วนกลับไปแย่ลงเรื่อยๆ ถ้าไม่มีอะไรมาคาน

**Loop ล่าง (load → rotation → load):** มีลิงก์ "−" หนึ่งเส้น (rotation → load) → นับได้ 1 (เลขคี่) → **B loop** — load หนักขึ้น ผลักดันให้ขยายขนาดทีม on-call ซึ่งพอทีมใหญ่ขึ้น load ต่อคนก็ลดลง (ลิงก์ลบ) ดึงกลับเข้าสู่จุดที่รับไหว

## ทำไมการอ่านออกว่ามีทั้ง R และ B ซ้อนกันถึงสำคัญ

ระบบ on-call fatigue นี้คือตัวอย่างจริงที่บริษัทเทคจำนวนมากเจอ — สิ่งที่ตัดสินว่าทีมจะ**ทรุดหนักลงเรื่อยๆ** (R ชนะ) หรือ **กลับมามั่นคงได้** (B ชนะ) ไม่ได้อยู่ที่ว่ามี loop ไหนอยู่ในระบบ (ทั้งสองมีอยู่พร้อมกันเสมอ) แต่อยู่ที่ **loop ไหนแรงกว่าในช่วงเวลานั้น** — ถ้าองค์กรขยายทีม (เปิด B loop ให้แรงพอ) ก่อนที่ R loop จะทันวนจน fatigue สะสมหนักเกินแก้ไข ระบบจะกลับสู่สมดุลได้ แต่ถ้าปล่อยให้ R loop วนไปหลายรอบก่อน (รอจน "เห็นปัญหาชัดๆ" ค่อยขยายทีม) ความล่าช้านั้นอาจทำให้ทีม burnout จนลาออกยกทีมไปแล้ว

นี่คือเหตุผลที่นักออกแบบระบบที่ดีไม่ได้ถามแค่ "มี feedback loop อะไรบ้าง" แต่ถามต่อว่า **"loop ไหนแรงกว่า ในช่วงเวลาไหน"** — คำถามนี้คือสะพานเชื่อมไปสู่หัวข้อสุดท้ายของโมดูลนี้ ซึ่งจะเติมตัวแปรที่เปลี่ยนว่า loop ไหนจะ "ชนะ" ได้อย่างมาก — นั่นคือ **delay**
