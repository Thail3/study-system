Deploy ล้มเหลวบ่อย ทุกครั้งที่เกิดขึ้น on-call engineer แก้ด้วยการ restart service ด้วยมือ ใช้เวลาไม่กี่นาที ปัญหาหาย ทุกคนไปต่อ ไม่มีใครมีเวลาไปสร้าง automated health-check + auto-rollback ที่แก้ปัญหาถาวร เพราะ "restart มือก็เร็วพออยู่แล้ว" ผ่านไปหนึ่งปี deploy fail ยังเกิดถี่พอๆ เดิม แถมตอนนี้มีแค่ 2 คนในทีมที่รู้วิธี restart ให้ถูกจุด ทีมกลายเป็นพึ่งพาสองคนนี้ตลอดเวลา ยิ่งไม่มีใครมีเวลาไปสร้างของถาวร เพราะสองคนนั้นยุ่งกับการดับไฟตลอด

## Shifting the Burden: ต่างจาก Fixes That Fail ตรงไหน

Fixes That Fail (หัวข้อก่อน) คือทางแก้ด่วนที่สร้าง**ผลข้างเคียงใหม่** ส่วน **Shifting the Burden** ร้ายกว่านั้นอีกขั้น — มันไม่ได้แค่สร้างผลข้างเคียง แต่ค่อยๆ **กัดกร่อนความสามารถของระบบในการสร้างทางแก้ถาวรด้วยตัวเอง** <mark class="hl-insight">ยิ่งพึ่งทางแก้ด่วนมากเท่าไหร่ ยิ่งไม่มีใครมีเวลา/แรงจูงใจไปสร้างทางแก้ถาวร</mark> กลายเป็นวงจร "เสพติด" ทางแก้ด่วนที่หลุดออกยากขึ้นเรื่อยๆ

## ทำไมมันหลุดออกยากขึ้นเรื่อยๆ

ธรรมชาติของ archetype นี้คือ ยิ่งเวลาผ่านไป ต้นทุนของการหันไปใช้ "ทางแก้ถาวร" ยิ่งสูงขึ้นเรื่อยๆ เพราะ capability ที่จะสร้างมันถูกกัดกร่อนไปเรื่อยๆ พร้อมกัน — <mark class="hl-warning">ทีมที่ปล่อยให้ archetype นี้ทำงานนานพอ มักถึงจุดที่ไม่มีใครในทีมมีความรู้/เวลาพอจะสร้างทางแก้ถาวรได้อีกแล้ว ต้องพึ่งพา "คนไม่กี่คนที่รู้ทางลัด" ตลอดไป ซึ่งพอคนเหล่านั้นลาออก ระบบทั้งหมดจะสั่นคลอนทันที</mark>

## ตัวอย่างที่พบบ่อยในองค์กร

| อาการ | ทางแก้ด่วน (B loop) | สิ่งที่ถูกกัดกร่อน (R loop) |
|---|---|---|
| Feature ซับซ้อนที่ทีมไม่ถนัด | จ้าง consultant ภายนอกมาทำให้ทุกครั้ง | ทีม in-house ไม่เคยได้ฝึกทำเองจนชำนาญ ต้องพึ่ง consultant ตลอดไป |
| Incident ที่ต้อง debug ซับซ้อน | ให้ "hero" คนเดียวที่รู้ระบบทั้งหมดเข้าไปแก้ทุกครั้ง | คนอื่นในทีมไม่เคยได้เรียนรู้ระบบส่วนนั้นลึกพอจะแก้เองได้ |
| Data ไม่ตรงกันระหว่างระบบ | แก้มือผ่าน SQL script เฉพาะกิจทุกครั้งที่เจอ | ไม่มีใครไปสร้าง data validation/reconciliation ที่ป้องกันปัญหาตั้งแต่ต้น |

## ทางออก: ตั้ง "เพดาน" ให้ทางแก้ด่วนตั้งแต่แรก

วิธีป้องกัน archetype นี้ที่ได้ผลจริงคือ **จำกัดขอบเขตของทางแก้ด่วนไว้ล่วงหน้าอย่างชัดเจน** เช่น กำหนดว่า manual restart ทำได้แค่ 2 ครั้งต่อเดือน ครั้งที่ 3 ต้องหยุดทุกงานอื่นแล้วสร้าง automated fix ทันที — <mark class="hl-insight">การตั้งกฎแบบนี้เท่ากับการเติม balancing loop เข้าไปคานไม่ให้ R loop วิ่งไปเรื่อยๆ โดยไม่มีใครหยุดมันเลย</mark>

หัวข้อถัดไปจะพาไปดู archetype ที่ต่างออกไปอีกแบบ — **Tragedy of the Commons** ซึ่งเกิดขึ้นเมื่อหลายฝ่ายแย่งใช้ทรัพยากรร่วมกัน โดยแต่ละฝ่ายมีเหตุผลที่ดีของตัวเองในการใช้มากขึ้น แต่รวมกันแล้วทำลายทรัพยากรนั้นสำหรับทุกคน
