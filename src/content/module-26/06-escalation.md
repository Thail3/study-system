Service A เรียก API ของ Service B แล้วเจอ timeout บ่อยๆ ทีม A เลยตั้ง retry ให้ถี่ขึ้นและ aggressive ขึ้น (retry 5 ครั้งแทน 2 ครั้ง) เพื่อรับมือ ผลคือ B ยิ่งโดน load ถล่มหนักขึ้น ยิ่ง timeout บ่อยขึ้นไปอีก ทีม B เห็นแบบนั้นก็ปรับ timeout ของตัวเองให้สั้นลงเพื่อ "fail fast ไม่ค้างนาน" ซึ่งทำให้ A เจอ error เร็วขึ้นและถี่ขึ้นกว่าเดิม A จึงยิ่งเพิ่ม retry อีก — วนแบบนี้ไปมาจนวันหนึ่งทั้งสองระบบโดน retry storm ถล่มพร้อมกันจนล่มทั้งคู่ ทั้งที่ไม่มีฝ่ายไหนทำอะไรที่ดูไม่สมเหตุสมผลเลยสักขั้นตอนเดียว

## Escalation: การตอบโต้ที่สมเหตุสมผลทีละก้าว รวมกันกลายเป็นหายนะ

**Escalation** ต่างจาก archetype อื่นในโมดูลนี้ตรงที่มันไม่ใช่ loop ที่วนอยู่ในฝ่ายเดียว แต่เป็น <mark class="hl-term">R loop เดียวขนาดใหญ่ที่สลับตัวตนไปมาระหว่างสองฝ่าย</mark> — การกระทำของ A กระตุ้นให้ B รู้สึกเสียเปรียบ B จึงตอบโต้ ซึ่งกระตุ้นให้ A รู้สึกเสียเปรียบอีกที วนกลับไปกระตุ้น A ต่อ ไม่มีจุดสิ้นสุดในตัวมันเอง

## จุดที่ทำให้ Escalation หลอกคนได้แนบเนียนที่สุด

จุดร่วมของทุกเคส escalation คือ **ในแต่ละก้าว การกระทำของแต่ละฝ่ายดูสมเหตุสมผลเสมอ** เมื่อมองแค่ก้าวนั้นก้าวเดียว — ทีม A เพิ่ม retry เพราะเจอ timeout จริง ทีม B ลด timeout เพราะไม่อยากค้างจริง ไม่มีฝ่ายไหนตั้งใจทำร้ายอีกฝ่าย แต่<mark class="hl-warning">พอมองภาพรวมทั้ง trajectory จะเห็นว่าผลสะสมพาทั้งสองฝ่ายไปไกลเกินกว่าที่ใครตั้งใจไว้แต่แรกมาก</mark> — นี่คือเหตุผลที่คนในสถานการณ์ escalation มักไม่รู้ตัวว่ากำลังอยู่ใน archetype นี้ เพราะทุกก้าวที่ตัวเองทำ "ดูมีเหตุผลดี" เสมอ

## ตัวอย่างที่พบบ่อย

| คู่ที่ตอบโต้กัน | สัญญาณของ Escalation |
|---|---|
| Timeout/Retry ระหว่างสอง service | ทั้งสองฝ่ายปรับ config ให้ aggressive ขึ้นเรื่อยๆ เพื่อตอบโต้พฤติกรรมของอีกฝ่าย |
| Code review gate ระหว่างสองทีมที่พึ่งพากัน | ทีมหนึ่งเข้มงวดขึ้นเพราะโดนอีกทีม merge โค้ดพังใส่ อีกทีมก็เข้มงวดตอบโต้ จนกระบวนการช้าลงเรื่อยๆ ทั้งคู่ |
| สงครามราคาระหว่างคู่แข่งธุรกิจ | ลดราคาตอบโต้กันไปมาจนมาร์จิ้นทั้งอุตสาหกรรมบางเฉียบ ไม่มีใครได้ประโยชน์จริง |
| Security team vs. เทคนิคหลบเลี่ยงของผู้โจมตี | มาตรการป้องกันเข้มขึ้น ผู้โจมตีปรับเทคนิคซับซ้อนขึ้นตอบโต้ วนไม่จบ (arms race แบบคลาสสิก) |

## ทางแก้: หยุดตอบโต้แบบสัมพัทธ์ แล้วตกลงเพดานร่วมกันแบบสัมบูรณ์

ทางแก้ของ escalation ไม่ใช่การ "ชนะให้ได้" (ยิ่งเร่ง loop ให้แรงขึ้น) แต่คือการ**หยุดวงจรการตอบโต้แบบสัมพัทธ์** (ปรับตามพฤติกรรมล่าสุดของอีกฝ่าย) แล้วเปลี่ยนไปใช้ **ข้อตกลงแบบสัมบูรณ์ที่ตกลงร่วมกันล่วงหน้า** แทน — เช่นสอง service ตกลง contract ร่วมกันเรื่อง timeout/retry policy ที่ชัดเจนแทนที่จะปรับตอบโต้กันเอง (มี SLA ที่ตกลงกันไว้), สองทีมตกลง code review SLA ร่วมกันแทนที่จะเข้มงวดขึ้นเรื่อยๆ ตามอารมณ์ล่าสุด — จุดสำคัญคือต้องมีคนหรือกลไกกลางที่มองเห็น **ทั้ง trajectory** ไม่ใช่แค่ก้าวล่าสุดของแต่ละฝ่าย เพราะแต่ละฝ่ายที่อยู่ในวงมักมองไม่เห็นภาพรวมนั้นด้วยตัวเอง

Escalation เกิดจาก R loop ที่ "ควรจะ" วิ่งไปเรื่อยๆ ทั้งด้านบวกและลบ — หัวข้อถัดไปจะพาไปดู archetype ที่โครงสร้างคล้ายกันแต่ทิศตรงข้าม: R loop ที่ "ควรจะ" วิ่งไปทางเติบโตต่อเนื่อง แต่กลับติดหล่มวนกลับทางลบได้ง่ายๆ จากความล่าช้าของการตัดสินใจลงทุน — **Growth and Underinvestment**
