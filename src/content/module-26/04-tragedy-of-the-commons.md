บริษัทมี CI runner pool กลางที่ทุกทีมใช้ร่วมกัน แต่ละทีมมีเหตุผลที่ดีของตัวเองในการรัน pipeline บ่อยๆ (feedback เร็ว = productivity ดี) ทีม A เพิ่ม pipeline trigger ถี่ขึ้น ทีม B ก็ทำเหมือนกัน <mark class="hl-warning">ทุกทีมตัดสินใจอย่างสมเหตุสมผลในมุมของตัวเอง แต่ผลรวมคือ runner pool คิวยาวจนทุกทีมต้องรอนานกว่าเดิม</mark> — ทุกคนแย่กันเองโดยไม่มีใครตั้งใจ นี่คือ **Tragedy of the Commons**

## โครงสร้าง: ทุกฝ่ายมี R loop ของตัวเอง แต่แชร์ B loop เดียวกันที่มองไม่ค่อยเห็น

## ทำไมทุกฝ่ายที่ "ตัดสินใจถูกต้อง" ถึงสร้างผลลัพธ์ที่แย่ร่วมกันได้

กุญแจของ archetype นี้คือความไม่สมมาตรระหว่างสองสิ่งที่แต่ละฝ่ายมองเห็น: **ผลตอบแทนจากการใช้ทรัพยากร มองเห็นชัดและเป็นของฝ่ายตัวเองทั้งหมด** (ใช้ CI runner บ่อย = ทีมตัวเองได้ feedback เร็ว) แต่ **ต้นทุนจากการใช้ทรัพยากรร่วม ถูกแบ่งกระจายให้ทุกฝ่ายรับไปคนละนิด** (คิวที่ยาวขึ้นกระทบทุกทีมเท่าๆ กัน ไม่ใช่แค่ทีมที่ใช้เยอะ) — <mark class="hl-insight">ทำให้แต่ละฝ่ายมองเห็นแรงจูงใจให้ "ใช้เพิ่ม" ชัดเจนกว่าแรงจูงใจให้ "ใช้น้อยลง" มาก แม้ในมุมรวมของทั้งองค์กรจะแย่กว่าเดิมก็ตาม</mark>

## ตัวอย่างที่พบในองค์กรเทค

| ทรัพยากรร่วม | พฤติกรรมที่แต่ละฝ่ายทำ (สมเหตุสมผลในมุมตัวเอง) | ผลรวมที่แย่ลง |
|---|---|---|
| CI/CD runner pool | ทุกทีมเพิ่มความถี่ pipeline trigger | คิวยาว ทุกทีมรอนานขึ้น |
| Shared staging environment | ทุกทีม deploy ทดสอบบ่อยๆ ไม่ประสานเวลา | Environment ไม่เสถียร ข้อมูลปนกัน ทดสอบไม่ได้ผลจริง |
| On-call engineer ที่เก่งที่สุดในทีม | ทุกทีมขอความช่วยเหลือจากคนคนนี้ก่อนเสมอ | คนนั้น burnout เร็ว กลายเป็น bottleneck และ risk ลาออก |
| งบประมาณ cloud รวมของบริษัท | แต่ละทีม provision resource เผื่อเกินจำเป็นเพื่อความชัวร์ของตัวเอง | ค่าใช้จ่ายรวมบานปลายเกินงบทั้งบริษัท |

## ทางแก้: ทำให้ต้นทุนที่กระจายอยู่ กลับมามองเห็นได้ชัดในระดับผู้ใช้แต่ละราย

ทางแก้ของ Tragedy of the Commons ไม่ใช่การขอร้องให้แต่ละฝ่าย "ใช้น้อยลงเพื่อส่วนรวม" (ไม่ยั่งยืน เพราะฝ่าฝืนแรงจูงใจของแต่ละคน) แต่คือการ**ออกแบบกลไกที่ทำให้ต้นทุนที่เคยกระจายไป กลับมาสะท้อนที่ผู้ใช้แต่ละรายโดยตรง** — เช่น ให้แต่ละทีมมี quota CI runner ของตัวเอง (ต้นทุนการใช้เกินโควตากลับมาที่ทีมนั้นโดยตรง ไม่กระจายให้คนอื่น), ทำ chargeback ค่า cloud แยกตามทีม, หรือมี rotation ที่บังคับกระจายภาระ on-call ไม่ให้กระจุกที่คนเก่งคนเดียว — หลักการเดียวกับที่ Elinor Ostrom (ผู้ได้รางวัลโนเบลเศรษฐศาสตร์จากงานวิจัยเรื่องนี้) พบในการจัดการทรัพยากรร่วมของชุมชนทั่วโลก: ทรัพยากรร่วมที่ยั่งยืนต้องมีกฎเกณฑ์ชัดเจนที่ทำให้ผู้ใช้แต่ละรายรับรู้ต้นทุนของตัวเองได้ ไม่ใช่ปล่อยให้กระจายจนไม่มีใครรู้สึกถึงมันเลย

หัวข้อถัดไปจะพาไปดู archetype ที่ต่างออกไปอีกมุม — **Success to the Successful** ซึ่งเกิดขึ้นเมื่อทรัพยากรถูกจัดสรรตามผลงานที่ผ่านมา จนฝ่ายที่เริ่มต้นได้เปรียบเล็กน้อย กลายเป็นได้เปรียบมหาศาลในระยะยาว
