ระบบตอบช้า ทีมแก้ด้วยการเพิ่ม cache หน้า query ที่ช้าที่สุด — ทันใดนั้น response time ดีขึ้นทันตา ทุกคนพอใจ ทีมย้ายไปทำงานอื่นต่อ ไม่มีใครกลับไป optimize query ตัวจริงอีกเลยเพราะ "cache แก้ให้แล้ว" หลายเดือนผ่านไป มีฟีเจอร์ใหม่มาใช้ query แบบเดียวกันซ้ำอีกหลายจุดโดยไม่รู้ว่ามันช้าโดยธรรมชาติ (เพราะไม่เคยเห็นมันช้าเลย มันถูก cache บังไว้ตลอด) วันที่ cache invalidate พร้อมกันตอน deploy ใหญ่ — database ทั้งฝูง query ที่ไม่เคย optimize พุ่งเข้าใส่พร้อมกัน ระบบล่มหนักกว่าตอนก่อนมี cache เสียอีก

## Fixes That Fail: ทางแก้ที่ดีในระยะสั้น กลายเป็นตัวสร้างปัญหาระยะยาว

**Fixes That Fail** คือ archetype ที่มีสอง loop ซ้อนกันบน "ทางแก้" เดียวกัน — <mark class="hl-term">B loop ที่บรรเทาอาการทันที กับ R loop ที่ค่อยๆ สร้างผลข้างเคียง</mark>ซึ่งย้อนกลับมาทำให้ปัญหาเดิมแย่ลงกว่าตอนไม่แก้เลยด้วยซ้ำ

## ตัวอย่างที่พบบ่อยในองค์กร

| ทางแก้ด่วน (B loop) | ผลข้างเคียงระยะยาว (R loop) |
|---|---|
| จ้าง contractor ด่วนมาเร่งงานให้ทันเดดไลน์ | ทีม in-house ไม่ได้เรียนรู้โดเมนนั้นเอง ต้องพึ่ง contractor ซ้ำตลอดไป |
| ลด scope การ test เพื่อ ship เร็วขึ้น | บั๊กหลุด production บ่อยขึ้น ต้องใช้เวลาแก้ hotfix มากกว่าเวลาที่ประหยัดไปตอนแรก |
| ให้ overtime พนักงานเพื่อเร่งโปรเจกต์ | Burnout สะสม ลาออกทีหลัง เสียเวลา ramp-up คนใหม่มากกว่าที่ประหยัดได้ |
| กู้เงินระยะสั้นดอกเบี้ยสูงเพื่อแก้ cash flow ตึงมือ | ภาระดอกเบี้ยยิ่งทำให้ cash flow ตึงกว่าเดิมในงวดถัดไป |

## วิธีตรวจจับก่อนจะสาย

คำถามที่ช่วยจับ archetype นี้ได้ตั้งแต่ต้นคือ: <mark class="hl-insight">**"ทางแก้นี้จัดการที่ต้นตอของอาการ หรือแค่กดอาการไว้ชั่วคราว"**</mark> ถ้าคำตอบคือกดอาการไว้ชั่วคราว ให้ถามต่อทันทีว่า **"มีอะไรที่กำลังสะสมอยู่เงียบๆ เบื้องหลังทางแก้นี้บ้าง"** — เช่น การเพิ่ม cache ควรมาพร้อมคำถามว่า "แล้วใครจะยัง optimize query ตัวจริงต่อ" ไม่ใช่ปล่อยให้ cache กลายเป็นข้ออ้างที่ทำให้ทุกคนลืมปัญหาต้นตอไปเลย

หัวข้อถัดไปจะพาไปดู archetype ที่ใกล้เคียงกันแต่ต่างกันตรงจุดสำคัญ — **Shifting the Burden** ซึ่งเกิดขึ้นเมื่อทางแก้ด่วนไม่ได้แค่สร้างผลข้างเคียง แต่ไป**ทำลายความสามารถของระบบในการแก้ปัญหาด้วยตัวเองในระยะยาว**
