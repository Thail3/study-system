พนักงานต้อนรับธนาคาร (จากบทที่แล้ว) รู้แล้วว่าต้องกระจายลูกค้าไปแต่ละช่อง แต่ยังมีคำถามหนึ่งที่ยังไม่ได้ตอบ: **จะตัดสินใจส่งลูกค้าไปช่องไหนด้วย "กฎ" อะไร** ลองนึกดูว่าพนักงานต้อนรับแต่ละคนอาจมีวิธีคิดไม่เหมือนกันเลย

## Round Robin — วนตามคิวเรียงลำดับ

พนักงานต้อนรับบางคนใช้วิธีง่ายที่สุด: ส่งลูกค้าคนแรกไปช่อง 1 คนที่สองไปช่อง 2 คนที่สามไปช่อง 3 แล้ววนกลับมาช่อง 1 ใหม่ ไม่สนใจอะไรเลยนอกจากลำดับ

วิธีนี้ **ง่ายที่สุด ไม่ต้องจำอะไรเยอะ** และถ้าลูกค้าแต่ละคนใช้เวลาที่เคาน์เตอร์พอๆ กัน (ฝากเงินธรรมดาทุกคน) ก็กระจายงานได้เท่าเทียมกันจริง — แต่ถ้าลูกค้าบางคนมาขอกู้บ้าน ใช้เวลาที่เคาน์เตอร์นานกว่าคนอื่นมาก <mark class="hl-warning">ช่องที่โดนลูกค้าประเภทนี้บ่อยๆ ก็จะยุ่งกว่าช่องอื่นทั้งที่ "ได้จำนวนลูกค้าเท่ากัน"</mark>

## Least Connections — ดูคิวจริงแล้วค่อยตัดสินใจ

พนักงานต้อนรับอีกแบบฉลาดกว่านั้นนิดหน่อย: **มองไปที่แต่ละช่องจริงๆ** ว่าตอนนี้ช่องไหนมีคนกำลังรอ/รับบริการอยู่น้อยที่สุด แล้วส่งลูกค้าคนใหม่ไปช่องนั้น

วิธีนี้เหมาะกับสถานการณ์ที่ลูกค้าแต่ละคนใช้เวลาไม่เท่ากัน (เหมือนตัวอย่างกู้บ้านข้างบน) เพราะช่องที่กำลังติดพันกับลูกค้าที่ใช้เวลานาน จะได้รับลูกค้าใหม่น้อยลงโดยอัตโนมัติ — แต่ก็ต้องแลกกับพนักงานต้อนรับต้องคอยสังเกตทุกช่องตลอดเวลา ไม่ใช่แค่จำเลขคิวเฉยๆ

## Random — สุ่มเลือกไปเลย

บางที่พนักงานต้อนรับก็ไม่คิดอะไรมาก แค่สุ่มชี้ไปช่องไหนก็ได้ที่ว่าง — ฟังดูมั่ว แต่ในทางสถิติ ถ้าลูกค้าเข้ามาเยอะมากพอ การสุ่มจะกระจายออกใกล้เคียงกับ round robin โดยไม่ต้องจำอะไรเลยด้วยซ้ำว่าส่งไปช่องไหนล่าสุด

## Consistent Hashing — ลูกค้าประจำ ไปหาคนเดิมทุกครั้ง

มีลูกค้าประเภทหนึ่งที่พนักงานต้อนรับมักจำหน้าได้ และตั้งใจส่งไปหาพนักงานคนเดิมทุกครั้งที่มา — เพราะพนักงานคนนั้นรู้ประวัติ รู้ความต้องการของลูกค้าคนนี้อยู่แล้ว ทำงานเร็วกว่าส่งไปหาคนใหม่ที่ต้องเริ่มทำความรู้จักใหม่หมด

ในทางเทคนิค เราไม่ได้ "จำหน้า" แต่ใช้การคำนวณ (hash) จากบางอย่างที่ระบุตัวลูกค้าได้ (เช่น user ID) แล้วแปลงเป็นเลขที่ชี้ไปยังเครื่องเดิมเสมอ ไม่ว่าจะมาติดต่อกี่ครั้งก็ตาม เทคนิคนี้เรียกว่า <mark class="hl-term">Consistent Hashing</mark> และจะเจออีกครั้งตอนเรียนเรื่อง **Caching** และ **Sharding** ในโมดูลถัดๆ ไป เพราะหลักการเดียวกันนี้ใช้ตัดสินใจว่า "ข้อมูลชิ้นนี้ควรอยู่เครื่องไหน" ได้ด้วย

    B -->|"Round Robin"| C["เครื่องถัดไปในคิว"]

## จำแค่คำถามเดียวก็พอ

ไม่ต้องท่องจำว่า algorithm ไหนดีที่สุด เพราะไม่มีอันไหนดีที่สุดตายตัว — <mark class="hl-insight">สิ่งที่ควรทำคือถามตัวเองสองคำถามก่อนเลือก: "งานแต่ละอันหนักเท่ากันไหม" (ถ้าไม่เท่า Least Connections มักดีกว่า) และ "ต้องการให้ลูกค้าคนเดิมกลับไปหาเครื่องเดิมไหม" (ถ้าใช่ ต้องใช้ Consistent Hashing)</mark> คำตอบสองข้อนี้จะพาไปหา algorithm ที่เหมาะเองโดยอัตโนมัติ

> ในสัมภาษณ์ ถ้าถูกถามว่า "จะเลือก algorithm ไหน" คำตอบที่ฟังดูเข้าใจจริงไม่ใช่การท่องชื่อ algorithm ทั้งหมด แต่คือการถามกลับด้วยสองคำถามข้างบนนี้ก่อน แล้วค่อยเลือกตามนั้น

## ขั้นสูง: Consistent Hashing ไม่ได้กระจายเท่ากันเสมอไป

Consistent Hashing แก้ปัญหา "ลูกค้าประจำต้องได้เครื่องเดิม" ได้จริง แต่มีข้อเสียที่ไม่ได้พูดถึง — <mark class="hl-warning">ถ้ามี server แค่ 3-4 เครื่อง การกระจาย key ไปตามค่า hash อาจไม่เท่ากันเลย บางเครื่องอาจได้ key ไปดูแลมากกว่าเครื่องอื่นหลายเท่า</mark> (เพราะตำแหน่งที่ hash ตกลงบน "วงกลม" ทางทฤษฎีเป็นการสุ่ม ไม่ได้การันตีว่าห่างเท่ากัน) ทางแก้ที่ใช้จริงคือ <mark class="hl-term">Virtual Nodes</mark> — แทนที่จะให้ server จริง 1 เครื่องมีจุดเดียวบนวงกลม hash ให้แต่ละเครื่องมีจุดปลอมหลายร้อยจุดกระจายทั่ววงกลม (server เดิมแค่ตอบรับ key จากทุกจุดปลอมของตัวเอง) ยิ่งมีจุดปลอมมากเท่าไหร่ การกระจายก็ยิ่งสม่ำเสมอขึ้นเรื่อยๆ ในทางสถิติ

อีกรูปแบบที่ระบบจริงเจอบ่อยคือเครื่องแต่ละเครื่อง**ไม่ได้แรงเท่ากัน** (เครื่องรุ่นใหม่แรงกว่าเครื่องรุ่นเก่าที่ยังใช้อยู่) — <mark class="hl-term">Weighted Round Robin / Weighted Least Connections</mark> แก้ตรงนี้โดยให้แต่ละเครื่องมี "น้ำหนัก" ตามกำลังจริง เครื่องแรงได้รับ request มากกว่าเครื่องอ่อนตามสัดส่วน ไม่ใช่แจกเท่ากันทุกเครื่องทั้งที่รับไหวไม่เท่ากัน

ระบบสมัยใหม่ (เช่น Envoy) นิยมใช้ <mark class="hl-term">Power of Two Choices (P2C)</mark> — สุ่มเลือก server 2 เครื่องมาเทียบกันก่อน แล้วส่ง request ไปเครื่องที่ active connection น้อยกว่า วิธีนี้ได้ผลใกล้เคียง Least Connections มาก โดยไม่ต้องเก็บสถานะทุกเครื่องแบบ real-time ทั้งระบบ (ซึ่งมี overhead สูงเมื่อเครื่องมีจำนวนมาก) — เป็นจุดกึ่งกลางที่คุ้มค่าระหว่างความแม่นยำกับต้นทุนในการรู้สถานะ

> คำถามสัมภาษณ์: "ทำไม Consistent Hashing แบบพื้นฐานกระจายงานไม่เท่ากันทั้งที่ตั้งใจให้เท่ากัน" — เพราะตำแหน่ง hash ของแต่ละเครื่องบนวงกลมเป็นไปตามการสุ่ม ไม่มีอะไรการันตีระยะห่างเท่ากัน ยิ่งจำนวนเครื่องน้อย ความเบี้ยวก็ยิ่งเห็นชัด ทางแก้คือเพิ่ม Virtual Nodes ให้แต่ละเครื่องจริงมีจุดปลอมหลายร้อยจุดกระจายทั่ววงกลม ทำให้กฎของจำนวนมาก (law of large numbers) ช่วยให้การกระจายสม่ำเสมอขึ้นเองโดยอัตโนมัติ
