ลองนึกภาพสองรูปแบบร้านอาหาร — แบบแรกคือ**ครัวเดียวทำทุกอย่าง** ตั้งแต่ก๋วยเตี๋ยว ส้มตำ ไปจนถึงของหวาน แม่ครัวคนเดียวหรือทีมเดียวรับผิดชอบทั้งหมด แบบที่สองคือ**ฟู้ดคอร์ท** ที่แต่ละร้านทำเมนูเฉพาะทางของตัวเอง ร้านก๋วยเตี๋ยวก็มีทีมของตัวเอง ร้านส้มตำก็มีทีมของตัวเอง แยกกันทำงานอิสระ แต่รวมกันอยู่ในห้างเดียวกัน

ทุกอย่างที่เรียนมา (load balancer, cache, database, queue) ใช้ได้ทั้งกับระบบที่เป็นครัวเดียว (<mark class="hl-term">Monolith</mark>) และระบบที่แตกเป็นฟู้ดคอร์ท (<mark class="hl-term">Microservices</mark>) — คำถามคือควรแตกเมื่อไหร่ และแตกแล้วได้อะไร เสียอะไร

## ต้นทุนที่มองไม่เห็นทันที

<mark class="hl-warning">แตกเป็นฟู้ดคอร์ทแล้วเรื่องที่เคยฟรี (เดินคุยกันในครัวเดียวกัน) กลายเป็นต้องจ่ายทุกครั้ง: ต้องเดินไปมาระหว่างร้าน (network latency), จัดการเวลาร้านหนึ่งขายหมดแต่อีกร้านยังขายอยู่ (partial failure), ทำบัญชีรวมข้ามหลายร้านยากกว่าบัญชีเดียว (distributed transaction)</mark>, และ**ต้องดูแลหลายร้านพร้อมกัน** (operational overhead) — สิ่งเหล่านี้คือเหตุผลที่ทีมเล็กมักเจ็บตัวถ้ารีบเปิดฟู้ดคอร์ทเร็วเกินไปทั้งที่ยังไม่มีลูกค้าพอจะเลี้ยงหลายร้าน

## ขั้นสูง: ทางเลือกกึ่งกลาง และฟู้ดคอร์ทปลอมที่แย่กว่าครัวเดียว

ไม่ต้องเลือกสุดขั้วระหว่าง Monolith เต็มตัว กับ Microservices เต็มตัว — ทางเลือกกึ่งกลางที่แนะนำกันบ่อยคือ <mark class="hl-term">Modular Monolith</mark> — ยังเป็นครัวเดียว deploy พร้อมกัน แต่**จัดโค้ดภายในให้แบ่งเป็นโมดูลที่ขอบเขตชัดเจน** (แต่ละโมดูลมี interface ชัด ไม่ยุ่งเกี่ยวกันมั่วๆ) เหมือนครัวเดียวที่แบ่งโซนทำงานชัดเจนภายใน แม้ยังไม่ต้องแยกร้าน <mark class="hl-insight">ถ้าวันหนึ่งต้องแตกจริง โมดูลที่ขอบเขตชัดอยู่แล้วแตกออกมาเป็น service ได้ง่ายกว่าโค้ดที่พันกันยุ่งเหยิงมาก</mark>

ปัญหาที่อันตรายกว่าคือ <mark class="hl-warning">Distributed Monolith — แตกโค้ดออกเป็นหลาย service ตามรูปร่างแล้ว แต่ยังผูกติดกันแน่นเหมือนเดิม (ใช้ database ตัวเดียวกันร่วมกัน, ต้อง deploy พร้อมกันเสมอเพราะ API ผูกกันแน่น, เรียกกันเป็นลูกโซ่จนแก้ที่หนึ่งกระทบทุกที่)</mark> — ผลคือได้ต้นทุนของ microservices (network latency, operational overhead) มาครบทุกอย่าง แต่ไม่ได้ประโยชน์ที่ตั้งใจจะได้เลยแม้แต่ข้อเดียว (deploy อิสระไม่ได้จริง, scale แยกไม่ได้จริง) — แย่กว่า Monolith เดิมเสียอีก

> คำถามสัมภาษณ์: "ทีมหนึ่งแตกเป็น 10 microservices แล้ว แต่ deploy ช้ากว่าเดิม ทำไม" — น่าจะเจอ Distributed Monolith: แตกโค้ดตามรูปร่างแล้วแต่ยังผูกกันแน่นเหมือนเดิม (shared database, API ผูกกันแน่นจนต้อง deploy พร้อมกันเสมอ) สัญญาณคือถ้ายังต้อง deploy หลาย service พร้อมกันทุกครั้งที่มีการเปลี่ยนแปลง แปลว่ายังไม่ได้ decouple จริง แค่แยกไฟล์เป็นก้อนๆ เท่านั้น — ต้องกลับไปดู boundary ระหว่าง service ใหม่ ไม่ใช่แค่จำนวน service ที่แยกออกมา
