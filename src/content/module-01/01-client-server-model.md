ลองนึกภาพร้านอาหารตามสั่งเจ้าหนึ่ง คุณนั่งที่โต๊ะ เปิดเมนู แล้วบอกพนักงานว่า "ขอผัดกะเพราหมูสับ ไข่ดาว" — คุณไม่ได้เดินเข้าไปทำเองในครัว คุณแค่**สั่ง** แล้วรอ พนักงานเดินใบสั่งเข้าไปให้ครัว ครัว**ทำ**อาหารแล้วส่งกลับมาให้คุณ

ระบบซอฟต์แวร์แทบทุกระบบทำงานด้วยหลักการเดียวกันเป๊ะ — มีฝั่งหนึ่งคอย "สั่ง" กับอีกฝั่งคอย "ทำ" ในวงการเรียกสองฝั่งนี้ว่า <mark class="hl-term">Client</mark> (ฝั่งสั่ง — เปรียบเหมือนตัวคุณที่นั่งอยู่โต๊ะ) กับ <mark class="hl-term">Server</mark> (ฝั่งทำ — เปรียบเหมือนครัวที่อยู่ข้างหลัง)

## ทำไมต้องแยกกันเป็นสองฝั่ง

ลองนึกภาพว่าไม่มีครัวกลาง — ลูกค้าแต่ละคนต้องทำอาหารกินเอง ถ้าอยากกินกะเพราแบบเดียวกับที่เพื่อนกิน ต้องขอสูตรมาทำเอง อยากรู้ว่าเมนูวันนี้มีอะไรบ้าง ก็ต้องไปถามคนอื่นทีละคน — วุ่นวายมาก

การมีครัวกลาง (Server) แก้ปัญหานี้ตรงๆ: <mark class="hl-insight">ข้อมูลอยู่ที่เดียว ทุกคนสั่งจากที่เดียวกัน</mark> ลูกค้าคนไหนสั่งกะเพราก็ได้สูตรเดียวกัน อยากรู้เมนูก็ดูจากที่เดียวกัน ไม่ต้องเก็บอะไรไว้เองเลย

## เดินตามใบสั่งดูสักครั้ง

พนักงานเสิร์ฟเดินใบสั่งจากโต๊ะไปครัว (**request**) ครัวทำเสร็จแล้วส่งจานอาหารกลับมาที่โต๊ะ (**response**) — สองคำนี้คือหัวใจของการสื่อสารระหว่าง client กับ server ทุกครั้งที่เปิดเว็บ กดปุ่มในแอป หรือแม้แต่เลื่อนดูฟีด เบื้องหลังก็คือใบสั่ง-จานอาหารแบบนี้เกิดขึ้นซ้ำๆ นับไม่ถ้วน

สังเกตว่า Client คอมกับ Client มือถือ **ไม่ได้คุยกันตรงๆ เลย** ทั้งคู่คุยกับ Server อย่างเดียว แต่กลับเห็นข้อมูลตรงกันได้ — นี่คือพลังของการมีศูนย์กลางเดียว เหมือนสองโต๊ะในร้านที่ไม่รู้จักกัน แต่กินกะเพราสูตรเดียวกันได้เพราะมาจากครัวเดียวกัน

## แล้วถ้าร้านคนแน่นล่ะ

ร้านอาหารตามสั่งเจ้าเล็กๆ มีครัวเดียว รับออเดอร์ทีละใบ ถ้าลูกค้าเยอะขึ้นเรื่อยๆ ครัวเดียวก็เริ่มทำไม่ทัน — คำถามนี้แหละที่ทุกเรื่องในหลักสูตรนี้จากนี้ไปจะตอบ: **จะออกแบบฝั่ง server ยังไงให้รับออเดอร์จำนวนมากได้เร็วและไม่ล่ม** ไม่ว่าจะเป็นเรื่อง load balancer (คนคอยจัดคิวลูกค้า), cache (จำเมนูฮิตไว้ไม่ต้องทำใหม่ทุกครั้ง), หรือ database replication (มีสูตรสำรองหลายชุดกันเผื่อชุดหนึ่งหาย) — ทั้งหมดคือวิธีทำให้ "ครัวกลาง" รองรับคนได้เยอะขึ้นโดยไม่เสียหลักการเดิม

## ขั้นสูง: ลูกค้าหลายแบบ กับสูตรเก่าที่ยังไม่มีใครยอมทิ้ง

ร้านอาหารในโลกจริงไม่ได้มีลูกค้าแบบเดียว — มีทั้งลูกค้าเดินเข้าร้าน คนสั่งผ่านแอป delivery คนโทรสั่งล่วงหน้า ระบบซอฟต์แวร์ก็เหมือนกัน: <mark class="hl-insight">Server เดียวมักต้องรับใบสั่งจาก client หลายแบบพร้อมกัน — เว็บ, แอป iOS, แอป Android, และบางทีก็ third-party ที่เรียก API ตรงๆ</mark> ปัญหาคือ**แอปมือถืออัปเดตไม่พร้อมกันทั้งหมด** — คนโหลดเวอร์ชันใหม่ทันที คนอีกกลุ่มไม่กดอัปเดตเป็นเดือนๆ (บางระบบพบว่าหลังออกเวอร์ชันใหม่ 6 เดือน ยังมี user หลักเปอร์เซ็นต์ค้างเวอร์ชันเก่าอยู่) ถ้า server เปลี่ยนรูปแบบใบสั่ง (API) แล้วลบของเก่าทิ้งทันที <mark class="hl-warning">แอปเวอร์ชันเก่าที่ยังมีคนใช้อยู่จะพังทันที ทั้งที่ผู้ใช้ไม่ได้ทำอะไรผิด</mark> — นี่คือเหตุผลที่ server มัก**ต้องรองรับ API หลายเวอร์ชันพร้อมกัน**ไปอีกนาน ก่อนจะถอดเวอร์ชันเก่าออกได้จริง (เจอรายละเอียดวิธีจัดการเวอร์ชัน API เต็มๆ ในโมดูล Microservices & API Design)

อีกเรื่องที่ต้องตัดสินใจคือ**ความคิด (logic) ควรอยู่ฝั่งไหน** — Client ตรวจกรอกฟอร์มให้ทันที (เร็ว ไม่ต้องรอ network) แต่ <mark class="hl-term">Server ต้องตรวจซ้ำเสมอ ห้ามเชื่อ client เด็ดขาด</mark> เพราะใครก็ปลอมแปลง request ตรงไปที่ server ได้โดยไม่ผ่านแอปเลย (เช่นใช้ curl ยิงตรง) การเช็คฝั่ง client คือช่วยเรื่อง**ประสบการณ์ใช้งาน** ส่วนการเช็คฝั่ง server คือ**ความปลอดภัยจริง** สองอย่างนี้ทำคู่กันเสมอ ไม่ใช่เลือกอย่างใดอย่างหนึ่ง

> คำถามสัมภาษณ์: "ทำไมต้อง validate ข้อมูลทั้งฝั่ง client และฝั่ง server ทั้งที่ดูซ้ำซ้อน" — เพราะทำหน้าที่ต่างกัน: client validate เพื่อ UX (ตอบสนองเร็ว ไม่ต้องรอ round-trip) ส่วน server validate เพื่อ security (client ปลอมแปลง/ข้ามได้เสมอ ไม่มีทางเชื่อ input จาก client 100%) ระบบที่ปลอดภัยต้อง treat ทุก request ที่มาถึง server เหมือนมาจากคนแปลกหน้าที่ยังไม่ตรวจสอบ ไม่ว่าจะมาจากแอปตัวเองหรือไม่ก็ตาม
