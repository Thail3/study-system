ร้านค้าออนไลน์เปิด flash sale สินค้า limited edition 100 ชิ้น ราคาพิเศษ นาฬิกาตั้งเวลาเปิดขาย 12:00:00 น. เป๊ะ คนกดพร้อมกันหมื่นกว่าคนในวินาทีเดียวกัน พอปิดการขาย ทีมพบว่ามี order ยืนยันสำเร็จ 587 รายการ ทั้งที่มีสินค้าจริงแค่ 100 ชิ้น — ต้องยกเลิกออเดอร์ 487 รายการ ลูกค้าโกรธจนเป็นข่าวลงโซเชียล

## ระดับที่ 1: Event

Order ยืนยันสำเร็จ 587 รายการ แต่คลังสินค้ามีจริงแค่ 100 ชิ้น ทีมต้องส่งอีเมลขอโทษและคืนเงินลูกค้า 487 คนที่ order ผ่านระบบแล้วแต่ไม่มีของจริงให้

## ระดับที่ 2: Pattern

ย้อนดู flash sale ที่เคยจัดมาแล้ว 4 ครั้ง พบว่า overselling เกิดซ้ำทุกครั้งไม่มีข้อยกเว้น และ<mark class="hl-insight">สัดส่วนที่ oversell แปรผันตรงกับความน่าดึงดูดของดีล — ดีลยิ่งดี คนยิ่งกดพร้อมกันมาก ยิ่ง oversell หนัก</mark> ครั้งแรก oversell แค่ 12 ชิ้น ครั้งนี้ oversell ไป 487 ชิ้น เพราะเป็นดีลที่แรงที่สุดเท่าที่เคยจัด

## ระดับที่ 4: Mental Model

ทีม e-commerce เชื่อว่า "cache ราคา/จำนวนสินค้าไว้ที่ edge server เพื่อความเร็วในการโหลดหน้าเว็บ" ก็เพียงพอแล้ว โดยไม่ตระหนักว่า **cache ที่ไม่ sync กับ database จริงแบบทันที ทำให้ทุก edge node เห็น "สินค้ายังเหลือ" พร้อมกันหมด** ทั้งที่ database จริงมีน้อยกว่านั้นมาก — root cause เดียวกับเคสก่อนหน้า (แยก read กับ write ออกจากกัน) แค่แฝงตัวอยู่ในอาการที่หน้าตาต่างไปโดยสิ้นเชิง

## Leverage Point ที่แนะนำ

1. **Parameter**: sync cache บ่อยขึ้น (ทุก 1 วินาทีแทน 30 วินาที) — ลด window ที่ผิดพลาดได้ แต่ไม่ปิดสนิท
2. **Structure**: ทำ reservation system ที่ตัด stock แบบ atomic ที่ database ตัวเดียว (single source of truth) ก่อนยืนยัน order ทุกครั้ง ไม่พึ่ง cache ในการตัดสินใจขาย
3. **Goals/Mental Model**: เปลี่ยนกรอบคิดจาก "แสดงจำนวนสินค้าคงเหลือแบบ real-time ให้เร็วที่สุด" (ซึ่งบังคับให้ต้องพึ่ง cache) เป็น "ความถูกต้องของ stock สำคัญกว่าความเร็วในการแสดงผล" — ยอมรับ eventual consistency ตอน "แสดง" จำนวนสินค้า แต่บังคับ strong consistency ตอน "ตัดสินใจขาย" จริง

## กลไกที่ทำงานจริง

**Parameter (sync cache บ่อยขึ้น) ทำไมถึงไม่ปิดปัญหา**: การ sync ถี่ขึ้นแค่ลด window ระหว่างที่ cache กับ database ไม่ตรงกัน เหมือน parameter fix ของเคสบอสดรอปไอเทม — โครงสร้าง check-then-act (เช็ค cache แล้วค่อยยืนยันขาย) ยังอยู่ครบ แค่ window แคบลง ซึ่งไม่พอเมื่อมี order นับหมื่นเข้ามาในวินาทีเดียว

**Structure (reservation system atomic) ทำไมถึงปิดปัญหาได้จริง**: หลักการเดียวกับเคสก่อนหน้าเป๊ะ — ย้ายจุดตัดสินใจออกจาก cache (ที่หลาย edge node เห็นค่าต่างเวลากันได้) ไปที่ database ตัวเดียวที่ atomic decrement บังคับให้ order ทุกตัวต้องเรียงคิวผ่านจุดเดียวกัน ไม่มีทางที่สอง order จะ "เห็น" stock เดียวกันพร้อมกันได้อีก — พิสูจน์ตรงตัวว่า root cause เดียวกันแก้ด้วยกลไกเดียวกันได้ข้ามอุตสาหกรรม

**Goals/Mental Model (ความถูกต้อง > ความเร็วในการแสดงผล) ทำไมถึงเป็น leverage ที่แรงกว่า**: ทางแก้นี้ไม่ได้พยายามทำให้ cache "แม่นขึ้น" แต่แยกหน้าที่ออกจากกันตั้งแต่ต้น — สิ่งที่ต้องเร็ว (แสดงผลหน้าเว็บ) ยอมให้คลาดเคลื่อนได้ ส่วนสิ่งที่ต้องถูก (การตัดสินใจขายจริง) บังคับ consistency เต็มรูปแบบ นี่คือการเปลี่ยนกรอบคิดว่าระบบหนึ่งไม่จำเป็นต้อง optimize คุณสมบัติเดียวทั้งระบบ

หัวข้อถัดไปเปลี่ยนโจทย์จากปัญหาแบบวินาทีเดียวจบ ไปเป็นปัญหาที่ค่อยๆ ฆ่าเกมทั้งเกมตลอดหนึ่งปีครึ่ง — **Matchmaking Queue Death Spiral**
