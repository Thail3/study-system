บริษัทหนึ่งมี CI/CD runner pool กลางให้ทุกทีมใช้ร่วมกัน แต่ละทีมเพิ่มความถี่ trigger pipeline ของตัวเองมากขึ้นเรื่อยๆ — trigger ทุก commit แทนที่จะ batch, retry ทันทีถ้า build ล้มเหลว — เพื่อความเร็วของทีมตัวเอง ผ่านไปหกเดือน คิว build เฉลี่ยยาวจาก 2 นาทีเป็น 40 นาที ทุกทีมเสียเวลารอมากกว่าที่เคยประหยัดได้จากการ trigger ถี่ขึ้นเสียอีก

## ระดับที่ 1: Event

ทีม X ร้องเรียนว่า PR ค้างอยู่ในคิว build นานถึง 40 นาที ทำให้ deploy ที่ควรเสร็จภายในวันเดียวกลายเป็นค้างข้ามวัน

## ระดับที่ 2: Pattern

ย้อนดู runner utilization ย้อนหลัง 6 เดือน พบว่าจำนวน job trigger ต่อวันเพิ่มขึ้นเรื่อยๆ **พร้อมกันทุกทีม** ไม่ใช่แค่ทีมเดียว ขณะที่จำนวน runner ที่บริษัทมีคงที่มาตลอด — คิวจึงยาวขึ้นเป็นเส้นตรงตามภาระรวมที่เพิ่ม

## ระดับที่ 4: Mental Model

ทุกทีมเชื่อเหมือนกัน: **"ทีมอื่นก็ทำแบบเดียวกันอยู่แล้ว ถ้าฉันไม่ trigger ถี่ ฉันจะเสียเปรียบ"** — นี่คือแก่นของปัญหา commons ทุกแบบ: การที่ทีมใดทีมหนึ่งยอมลดความถี่ trigger ลงเองฝ่ายเดียว แทบไม่ช่วยลด load รวมเลย (ทีมอื่นยังใช้เท่าเดิม) จึงไม่มีทีมไหนมีแรงจูงใจเป็นฝ่ายแรกที่ "เสียสละ"

## Leverage Point ที่แนะนำ

1. **Parameter**: เพิ่มจำนวน runner — ช่วยได้ชั่วคราว แต่ demand จะขยายมาเติมเต็ม capacity ใหม่อีกถ้าไม่เปลี่ยนแรงจูงใจ (เหมือนทุ่งหญ้าสาธารณะที่ขยายแล้วก็ถูกเลี้ยงสัตว์จนโล้นอีก)
2. **Structure**: ให้แต่ละทีมมี quota runner ของตัวเอง — ต้นทุนการใช้เกิน quota กลับมาที่ทีมนั้นโดยตรง ไม่กระจายให้คนอื่นรับแทน (เชื่อมกับ chargeback ที่เจอในโมดูล Systems Archetypes)
3. **Goals/Mental Model**: เปลี่ยนกรอบคิดจาก "แต่ละทีม optimize velocity ของตัวเอง" เป็น "ทั้งบริษัท optimize total delivery throughput ร่วมกัน" — วัดผลจาก deployment frequency ระดับองค์กร ไม่ใช่ velocity แยกทีมใครทีมมัน

## กลไกที่ทำงานจริง

**Parameter (เพิ่ม runner) ทำไมถึงถูก Demand เติมเต็มใหม่**: จากไดอะแกรมด้านบน ลิงก์ trigger→load ของทั้งสอง R loop ยังไม่ถูกแตะเลย เพิ่ม capacity คือการขยาย "ทุ่งหญ้า" แต่แรงจูงใจให้แต่ละทีม trigger ถี่ขึ้นเมื่อรู้สึกว่ามี capacity เหลือยังอยู่เหมือนเดิม demand จึงขยายมาเติมเต็ม capacity ใหม่จนช้าลงอีกในที่สุด

**Structure (quota ต่อทีม) ทำไมถึงอ่อนแรง Loop ได้จริง**: การให้ quota แยกทีมเปลี่ยน node "load" จาก pool กลางที่ไม่มีเจ้าของ เป็นเพดานที่ผูกกับแต่ละทีมโดยตรง — ลิงก์ trigger→load ของทีมหนึ่งไม่กระทบทีมอื่นอีกต่อไป เพราะต้นทุนของการ trigger เกินไปกลับมาที่ผู้สร้างต้นทุนเอง ไม่กระจายให้ใครแบกร่วมอีก

**Goals/Mental Model (org-wide throughput) ทำไมถึงตัดต้นตอของแรงจูงใจ**: สองทางแก้ข้างบนยังปล่อยให้ "velocity ทีมตัวเอง" เป็นสิ่งที่แต่ละทีม optimize อยู่ ซึ่งคือแรงขับของทั้งสอง R loop ตั้งแต่แรก — พอเปลี่ยนตัวชี้วัดเป็น throughput รวมทั้งองค์กร การ trigger ถี่เกินจำเป็นของทีมหนึ่งจะกลายเป็นต้นทุนต่อ metric เดียวกันที่ทีมนั้นเองกำลังพยายามทำให้ดีขึ้น ไม่ใช่ externalities ที่ไม่มีใครรับผิดชอบอีกต่อไป

หัวข้อถัดไปเปลี่ยนจากปัญหาที่ทุกฝ่ายเห็นชัดเจนอยู่แล้ว ไปเป็นปัญหาที่ผู้บริหารมองไม่เห็นเลยเพราะตัวเลขที่ใช้ตัดสินใจถูกบิดเบือนอยู่แล้วตั้งแต่ต้น — **Support Team ที่ Headcount นิ่งทั้งที่ผู้เล่นโตต่อเนื่อง**
