โมดูลสุดท้ายของ track นี้ เอาเครื่องมือทั้งหมดที่เรียนมา — stock/flow, feedback loop, archetype, leverage point, iceberg model — มาไล่กับปัญหาจริงสามเคสทีละขั้น เริ่มจากเคสที่คุ้นเคยที่สุด: **Technical Debt** ที่เจอมาแล้วหลายครั้งกระจายอยู่ทั่ว track

## ระดับที่ 1: Event

ทีม A ต้องใช้เวลา 3 วันในการเพิ่ม field ใหม่ตัวเดียวเข้าไปใน checkout flow ทั้งที่ควรใช้เวลาไม่ถึงครึ่งวัน เพราะโค้ดส่วนนั้นพันกันยุ่งเหยิงจนแก้ตรงไหนก็กระทบที่อื่นโดยไม่คาดคิด

## ระดับที่ 2: Pattern

ดูย้อนหลัง 6 เดือน พบว่าเวลาเฉลี่ยที่ใช้ต่อ feature ใน module checkout เพิ่มขึ้นเรื่อยๆ ทุกเดือน (จาก 2 วัน เป็น 3 วัน เป็น 4.5 วัน) ขณะที่ module อื่นในระบบเดียวกันเวลาคงที่ — นี่คือกราฟทรง **exponential** ที่เจอในโมดูล Behavior Patterns

## ระดับที่ 4: Mental Model

สัมภาษณ์ทีมแล้วพบความเชื่อร่วมที่ไม่เคยถูกพูดออกมาตรงๆ: **"Refactor คือสิ่งที่ทำตอนมีเวลาว่างเท่านั้น ไม่ใช่งานที่ควรจัดสรรเวลาไว้ล่วงหน้าเหมือนงานอื่น"** — <mark class="hl-insight">mental model นี้เองที่ทำให้ outflow ไม่เคยถูกเปิดเลยตลอด 6 เดือน ไม่ใช่เพราะทีมขี้เกียจหรือไม่เห็นปัญหา แต่เพราะความเชื่อพื้นฐานที่ว่า refactor "ไม่ใช่งานจริง" ทำให้มันแพ้ทุกครั้งเวลาต้อง prioritize กับงานอื่นที่ถูกมองว่า "งานจริง" มากกว่า</mark>

## Leverage Point ที่แนะนำ

ตามกฎจากโมดูล Leverage Points — ลองจากอ่อนไปแรง:

1. ~~Parameter~~ (ปรับ coding standard เอกสาร) — ลองมาแล้ว ไม่ได้ผล เพราะไม่มีเวลาทำตามจริง
2. **Structure** — จัดสรร 20% sprint capacity ให้ refactor แบบบังคับทุก sprint (เปิด outflow ให้ไม่เป็นศูนย์อีกต่อไป) — จุดเริ่มต้นที่ทำได้ทันที
3. **Goals/Mental Model** — เปลี่ยนนิยาม "Definition of Done" ของทีมให้รวม "ไม่เพิ่ม complexity เกินเกณฑ์ที่ตั้งไว้" เข้าไปด้วย ไม่ใช่แค่ "feature ทำงานได้" — นี่คือการแก้ที่ mental model โดยตรง เปลี่ยนสิ่งที่ทีมนับว่าเป็น "งานเสร็จจริง"

## กลไกที่ทำงานจริง

**Parameter (coding standard เอกสาร) ทำไมถึงไม่ได้ผล**: เอกสารมาตรฐานไม่มีกลไกบังคับใดๆ เชื่อมกลับไปที่การตัดสินใจจัดสรรเวลาจริงในแต่ละ sprint เลย — มันคือกฎที่เขียนไว้เฉยๆ ไม่ใช่วาล์วที่บังคับให้ outflow เปิด ผลคือ outflow ยังเป็นศูนย์เหมือนเดิมทุกประการ ไม่ต่างจากก่อนมีเอกสารเลย

**Structure (บังคับ 20% sprint capacity) ทำไมถึงเปิด Outflow ได้จริง**: จากไดอะแกรมด้านบน stock (tech debt) จะลดได้ก็ต่อเมื่อ outflow มีค่ามากกว่าศูนย์เท่านั้น — การบังคับสัดส่วน sprint capacity ไม่ใช่แค่ "ขอให้ทำ" แต่คือการสร้างวาล์วที่เปิดทุกรอบ sprint ไม่ว่างานอื่นจะแย่งเวลาแค่ไหน หลักการนี้ตรงกับ stock/flow พื้นฐาน: stock จะไม่มีวันลดถ้า outflow ถูกปล่อยให้แพ้ inflow ทุกครั้งที่ต้อง priority

**Goals/Mental Model (เปลี่ยนนิยาม Definition of Done) ทำไมถึงเป็น leverage ที่แรงกว่า**: สองทางแก้ข้างบนแก้ที่ outflow (ระบายหนี้ที่มีอยู่แล้ว) แต่ทางนี้แก้ที่ **inflow** โดยตรง — ถ้า "เพิ่ม complexity เกินเกณฑ์" ไม่นับว่า "เสร็จ" ตั้งแต่แรก debt ใหม่จะไม่ถูกสร้างขึ้นมาให้ต้องระบายทีหลังเลย เหมือนการปิดก๊อกน้ำแทนที่จะเปิดท่อระบายให้กว้างขึ้นเฉยๆ — นี่คือทำไมมันเป็นการแก้ที่ mental model จริง ไม่ใช่แค่ process

การไล่ทั้ง 4 ระดับของ event เดียว (checkout ช้า) แสดงให้เห็นว่าทำไมการแก้แค่ผิวน้ำ (จ้างคนเก่งมาช่วยเร่ง feature นี้ให้เสร็จ) จะไม่มีวันแก้ปัญหาถาวร ต้องขุดลงไปถึง structure และ mental model ถึงจะเจอจุดที่แก้แล้วปัญหาไม่กลับมาอีก
