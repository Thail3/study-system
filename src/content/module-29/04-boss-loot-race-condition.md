บอสตัวหนึ่งในเกม MMO ถูกผู้เล่น 1,000 คนรุมตีพร้อมกัน พอบอสตาย ระบบดรอปไอเทมหายากออกมาชิ้นเดียว — ทุกคนกดปุ่ม "เก็บ" ในเสี้ยววินาทีเดียวกัน ผลลัพธ์: มีคนได้ไอเทม 1 คน อีก 999 คนเห็นข้อความ "มีคนเก็บไปแล้ว" ปัญหาคือ ticket ร้องเรียนที่เข้ามาไม่ใช่แค่ "แพ้แล้วเสียใจ" — มันคือ "ผมกดก่อนเห็นๆ ทำไมถึงไม่ได้"

## ระดับที่ 1: Event

รายงานจาก support ทุกสัปดาห์ระบุแบบเดียวกันซ้ำๆ: ผู้เล่นยืนยันว่ากดเก็บไอเทมก่อน แต่ระบบมอบให้คนอื่น ทีม support ไม่มีคำตอบที่ดีกว่า "ระบบทำงานตามที่ควรจะเป็น" ซึ่งฟังดูไม่น่าเชื่อสำหรับผู้เล่นที่เห็นตัวเองกดก่อนจริงๆ

## ระดับที่ 2: Pattern

ดู log ย้อนหลังพบว่าทุกครั้งที่บอสตาย มี request "เก็บไอเทม" หลักร้อยรายการเข้ามาพร้อมกันภายในช่วงเวลาไม่ถึง 50 มิลลิวินาที — เป็น spike ที่ทำนายล่วงหน้าได้เป๊ะทุกครั้ง (เกิดตรงจังหวะบอสตายเสมอ) แต่ที่น่าสนใจกว่านั้นคือ: <mark class="hl-insight">ผู้เล่นที่ชนะซ้ำๆ มักเป็นกลุ่มเดิม — ไม่ใช่เพราะโชค แต่เพราะ ping ต่ำกว่า request ถึง server เร็วกว่าคนอื่นเสมอ</mark>

ต้นตอทางเทคนิคคือ <mark class="hl-term">**check-then-act race condition**</mark> — server เช็คก่อนว่าไอเทมยังอยู่ไหม (read) แล้วค่อยมอบให้ (write) สองขั้นตอนแยกกัน ถ้ามี 2 request เข้ามาในช่วงเวลาระหว่าง read กับ write ของกันและกัน ทั้งคู่จะอ่านเห็น "ไอเทมยังอยู่" พร้อมกัน แล้วทั้งคู่ก็เชื่อว่าตัวเองได้ — <mark class="hl-warning">แต่ปัญหาที่ลึกกว่านั้นคือโครงสร้างการแข่งขันเอง ทำให้คนที่ได้เปรียบด้าน network (ping ต่ำ) ชนะซ้ำแล้วซ้ำเล่า — นี่คือ Success to the Successful (จากโมดูล Systems Archetypes) แฝงอยู่ในคราบของ bug ทางเทคนิค</mark>

## ระดับที่ 4: Mental Model

ทีมพัฒนามีความเชื่อฝังมาตั้งแต่ตอนออกแบบระบบครั้งแรก ซึ่งตอนนั้น server หนึ่งมีผู้เล่นแค่ไม่กี่สิบคน: **"เช็คแล้วเขียนสองขั้นตอนแยกกันไม่เป็นไร เพราะโอกาสชนพร้อมกันจริงมีน้อยมาก"** — mental model นี้ถูกต้องตอน scale เล็ก แต่กลายเป็นเท็จทันทีที่ scale ใหญ่ขึ้นเป็น 1,000 คนต่อบอสหนึ่งตัว ไม่มีใครกลับมาทบทวนสมมติฐานนี้อีกเลยตลอดหลายปีที่เกมโตขึ้น

## Leverage Point ที่แนะนำ

1. **Parameter**: เพิ่ม server tick rate ให้ประมวลผลเร็วขึ้น — ลด window ที่ race เกิดได้ แต่ไม่ปิดสนิท ยังพังได้ถ้า concurrent เยอะพอ
2. **Structure**: เปลี่ยนจาก check-then-act เป็น atomic operation เดียว (compare-and-swap หรือ row lock ระดับ database) ให้ server ตัดสินผู้ชนะแบบ atomic จริงๆ — ปิดช่องว่างที่ race เกิดได้ทั้งหมด
3. **Goals/Mental Model**: เปลี่ยนกรอบคิดทั้งระบบจาก "ต้องมีผู้ชนะ 1 คน" (zero-sum ที่บังคับให้มีคนแพ้ 999 คนเสมอ) เป็น "ทุกคนที่ร่วมตีบอสได้ไอเทมของตัวเอง" (personal loot instancing — แนวทางที่เกมสมัยใหม่ส่วนใหญ่ใช้) นี่คือการแก้ที่ mental model จริงๆ ไม่ใช่แค่แก้ bug แต่เปลี่ยนกติกาทั้งระบบให้ scarcity ที่เป็นต้นตอของปัญหาหายไปเลย

## กลไกที่ทำงานจริง

**Parameter (เพิ่ม tick rate) ทำไมถึงไม่พอ**: ดูจากไดอะแกรมด้านบน — การเพิ่ม tick rate ไม่ได้แก้ไขรูปร่างของ flow "claim" เลยแม้แต่นิดเดียว มันแค่ทำให้ **window เวลาระหว่าง read กับ write แคบลง** เช็ค-แล้ว-เขียนสองขั้นตอนที่แยกกันยังคงแยกกันอยู่เหมือนเดิมทุกประการ เพียงแต่ช่วงเวลาที่ request สองตัวจะ "ชนกันพอดี" สั้นลง — จาก pattern ที่เห็น (500 request ใน 50 มิลลิวินาที) ต่อให้ window เหลือแค่ 1 มิลลิวินาที ก็ยังมีโอกาสสูงที่จะมี 2 request ตกอยู่ใน window เดียวกันได้อยู่ดี เพราะ**โครงสร้าง**ของปัญหา (flow ที่ไม่ atomic) ไม่ได้เปลี่ยน แค่ความน่าจะเป็นเปลี่ยน

**Structure (atomic operation) ทำไมถึงปิดปัญหาได้จริง**: หลักการ stock/flow ที่เรียนมาตั้งแต่โมดูล Stocks and Flows คือ **flow ที่ไหลออกจาก stock ต้องมี "วาล์ว" เดียวควบคุมอยู่เสมอ** — ปัญหาเดิมคือ flow "claim" ไม่มีวาล์วจริง มันปล่อยให้หลาย request "มอง" เข้าไปที่ stock พร้อมกันได้ก่อนตัดสินใจ compare-and-swap เปลี่ยนสิ่งนี้ให้กลายเป็นวาล์วเดียวที่ทุก request ต้องเรียงคิวผ่าน — ไม่ใช่แค่ทำให้ race "เกิดยากขึ้น" แบบ parameter แต่ทำให้ race **เกิดไม่ได้เลยในทางโครงสร้าง** เพราะไม่มีจังหวะไหนที่ 2 request จะ "เห็น" สถานะเดียวกันของ stock พร้อมกันได้อีกต่อไป

**Goals/Mental Model (personal loot instancing) ทำไมถึงเป็น leverage ที่แรงที่สุด**: สองทางแก้ข้างบนยังคงมี "stock ที่ถูกแย่งชิง" อยู่ — แค่แย่งชิงกันแบบยุติธรรมขึ้น (structure) หรือน่าจะยุติธรรมขึ้น (parameter) ทางแก้นี้ตัดปัญหาที่รากไปเลย: เปลี่ยนจาก **1 stock ที่มีหลาย flow เข้าแย่งกัน** เป็น **1,000 stock อิสระ ที่แต่ละอันมี flow เข้าแค่เส้นเดียว** — Success to the Successful (จากโมดูล Systems Archetypes) ต้องการทรัพยากรจำกัดที่ใช้ร่วมกันถึงจะเกิดได้ พอไม่มีการใช้ร่วมกันอีกต่อไป archetype นั้นก็ไม่มีเงื่อนไขให้เกิดขึ้นเลย — นี่คือความต่างระหว่างการ "แก้ปัญหาให้ดีขึ้น" กับการ "ทำให้ปัญหานั้นไม่มีอยู่จริง" ซึ่งเป็นสิ่งที่ leverage point ระดับ goals/paradigm ทำได้ แต่ระดับ parameter/structure ทำไม่ได้
