เกมมือถือเกมหนึ่งถูก feature บนหน้าแรก App Store ในวันเปิดตัว ยอด download พุ่งแบบทวีคูณ ทีมดีใจเห็นตัวเลขทะลุเป้า 10 เท่า — แต่ 3 ชั่วโมงหลังเปิดตัว server ล่มทั้งหมด ตรงจังหวะที่ media coverage และความสนใจของคนพีคที่สุดพอดี โอกาสที่ควรจะดีที่สุดในชีวิตของเกม กลับกลายเป็นวันที่แย่ที่สุด

## ระดับที่ 1: Event

Server ตอบสนองไม่ได้ทั้งหมดตั้งแต่ 15:32 น. ของวันเปิดตัว ผู้เล่นใหม่ที่เพิ่งโหลดเกมเจอหน้าจอ error ทันทีที่เปิดแอปครั้งแรก

## ระดับที่ 2: Pattern

กราฟ concurrent user ตั้งแต่เปิดตัว: นิ่งขึ้นแบบทวีคูณตลอด 3 ชั่วโมงแรก แล้วดิ่งลงแรงกว่าตอนขึ้นมาก — <mark class="hl-insight">ตรงกับทรงกราฟ overshoot and collapse ที่เจอในโมดูล Behavior Patterns เป๊ะ ไม่ใช่แค่ "โตแล้วพัง" ธรรมดา แต่โตเร็วมากจนพังแรงกว่าที่ควรจะเป็น</mark>

โครงสร้างนี้คือ R loop ที่วิ่งชนขีดจำกัด (carrying capacity ของ server) ที่ B loop ตอบสนองไม่ทัน — <mark class="hl-warning">ทีมเตรียม capacity ไว้ "10 เท่าของค่าเฉลี่ยที่คาดการณ์" ซึ่งฟังดูเผื่อเยอะมาก แต่ App Store feature ไม่ใช่การเติบโตแบบค่อยเป็นค่อยไป — มันคือ spike ที่ทวีคูณเร็วกว่าที่ capacity planning แบบเดิมรองรับได้ทัน</mark>

## ระดับที่ 4: Mental Model

ทีมเชื่อว่า **"เตรียม capacity ไว้หลายเท่าของค่าเฉลี่ยที่คาดก็เกินพอแล้ว"** — ความเชื่อนี้ใช้ได้กับการเติบโตแบบค่อยเป็นค่อยไป แต่ล้มเหลวโดยสิ้นเชิงกับ spike แบบ viral ที่ไม่มีสัญญาณเตือนล่วงหน้าเพียงพอให้ scale ทัน — ทีมไม่เคยตั้งคำถามว่า "ถ้า capacity ที่เตรียมไว้ไม่พอจริงๆ ขึ้นมา ระบบควรพังแบบไหน" เพราะสมมติฐานทั้งหมดตั้งอยู่บนฐานว่า "คงไม่มีวันไม่พอหรอก"

## Leverage Point ที่แนะนำ

1. **Parameter**: เพิ่ม auto-scale ให้แรงขึ้น/ตั้ง buffer capacity ไว้ล่วงหน้าก่อน launch — ช่วยยืดขีดจำกัดออกไปได้ แต่ยังมีเพดานจำกัดอยู่ดี
2. **Structure**: ทำ graceful degradation — เช่น queue ระบบเข้าเกมแทนการปฏิเสธตรงๆ, ปิด feature หนักๆ ชั่วคราวตอน load สูงมาก (ลด scope ของสิ่งที่ต้องรองรับ แทนที่จะพังทั้งระบบ)
3. **Goals/Mental Model**: เปลี่ยนกรอบวางแผน capacity จาก "ประมาณการเฉลี่ยที่คาดไว้" เป็น "ออกแบบระบบให้ fail gracefully เสมอเมื่อเกินขีดจำกัด" — เพราะไม่มีทางคาดการณ์ viral spike ได้แม่นยำ 100% ทุกครั้ง คำถามที่ถูกต้องไม่ใช่ "จะไม่มีวันพังใช่ไหม" แต่คือ "ถ้าพัง จะพังแบบไหนที่กระทบน้อยที่สุด"

## กลไกที่ทำงานจริง

**Parameter (auto-scale/buffer) ทำไมถึงแค่ย้ายเพดาน ไม่ลบมัน**: จากไดอะแกรมด้านบน R loop ล่าง (load→crash→downloads(-)) ยังคงอยู่ครบ การเพิ่ม buffer แค่ดันเพดานที่ loop นี้จะเริ่มทำงานให้ไกลออกไป — ถ้า spike แรงกว่าที่ buffer เผื่อไว้ (ซึ่งคาดเดาแม่นยำไม่ได้) loop เดิมก็ยังทำงานเหมือนเดิมทุกประการ แค่ที่ตัวเลขสูงกว่า

**Structure (graceful degradation) ทำไมถึงตัด Loop ได้จริง**: การ queue คนเข้าเกมหรือปิด feature หนักชั่วคราว ไม่ได้พยายามเลื่อนเพดานออกไป แต่เปลี่ยนสิ่งที่เกิด **ที่** เพดานนั้นโดยตรง — แทนที่ load สูงจะนำไปสู่ crash เต็มรูปแบบ (ซึ่งจุดลิงก์ crash→downloads(-) ให้ทำงานแรง) ระบบแค่ทำงานช้าลงแต่ยังอยู่ ตัดลิงก์ load→crash ไม่ให้แปลงเป็น crash เต็มระบบ

**Goals/Mental Model (design for graceful failure) ทำไมถึงเป็น leverage ที่แรงที่สุด**: สองทางแก้ข้างบนยังพนันอยู่กับการเดา threshold ที่ถูกต้องล่วงหน้า — ทางนี้เปลี่ยนคำถามจาก "capacity จะพอไหม" (ตอบไม่ได้แน่นอนสำหรับ viral spike) เป็น "ถ้าไม่พอ จะพังแบบไหนที่กระทบน้อยที่สุด" ซึ่งเป็นคำถามที่ตอบล่วงหน้าได้เสมอไม่ว่า spike จะแรงแค่ไหนจริงๆ

หัวข้อถัดไปเปลี่ยนจากปัญหาที่ทุกคนเห็นตรงกันว่าเป็นปัญหา ไปเป็นปัญหาที่ทั้งสองทีมต่างเชื่อว่าตัวเองกำลังทำสิ่งที่ถูกต้องอยู่แล้ว — **ทีม Game Design vs ทีม Live-Ops ที่ทำลายกันโดยไม่รู้ตัว**
