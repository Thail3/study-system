ลองนึกภาพสองวิธีเก็บเอกสารในบ้าน — วิธีแรกคือ**ตู้เอกสารที่มีช่องแบ่งเป็นระเบียบ** ทุกใบต้องเข้าฟอร์มเดียวกัน มีป้ายกำกับชัดเจนว่าใบนี้ต้องอยู่ช่องไหน หมวดไหน หาอะไรก็เจอเร็วเพราะทุกอย่างเป็นระบบ วิธีที่สองคือ**กล่องเก็บของอเนกประสงค์** ใส่อะไรก็ได้ลงไป ไม่ต้องจัดหมวดหมู่ล่วงหน้า สะดวกเวลาต้องรีบเก็บของแปลกๆ ที่ไม่เข้าฟอร์มไหนเลย แต่พอของเยอะขึ้นจะเริ่มหายากขึ้นเรื่อยๆ

ทุกระบบต้องเก็บข้อมูลถาวรที่ไหนสักที่ — สองทางเลือกหลักคือ **SQL (Structured Query Language, relational)** ซึ่งเหมือนตู้เอกสารมีระเบียบ กับ <mark class="hl-term">NoSQL</mark> ซึ่งเหมือนกล่องอเนกประสงค์ <mark class="hl-insight">ไม่ใช่ว่าอันไหนดีกว่าเสมอ แต่เหมาะกับรูปแบบข้อมูล/การใช้งานต่างกัน</mark>

## ตัวอย่างที่เหมาะกับกล่องอเนกประสงค์ (NoSQL)

เช่น log เหตุการณ์, ข้อความแชท, ข้อมูล sensor จาก IoT (Internet of Things — อุปกรณ์ที่เชื่อมเน็ตได้ เช่น เซนเซอร์อุณหภูมิ, กล้องวงจรปิด) — เขียนถี่มาก ข้อมูลแต่ละชิ้นไม่ต้องเชื่อมกับอะไร (โยนใส่กล่องแล้วจบ ไม่ต้องหาว่าใบนี้เข้าฟอร์มไหน) NoSQL scale การเขียนแนวนอนได้ง่ายกว่าตู้เอกสารที่มีระบบมาก เพราะไม่ต้องคอยรักษาความสัมพันธ์ระหว่างข้อมูล

## ในทางปฏิบัติ

ระบบใหญ่มัก**ใช้ทั้งคู่พร้อมกัน** — เอกสารสำคัญที่ต้องเชื่อมโยงกันแน่นหนา (user, order, payment) เก็บในตู้เอกสารมีระบบ (SQL) ส่วนของที่เก็บเร็วๆ ไม่ต้องจัดระเบียบมาก (log, session cache, chat history) โยนใส่กล่องอเนกประสงค์ (NoSQL) — เรียกแนวทางนี้ว่า <mark class="hl-term">polyglot persistence</mark>

## ขั้นสูง: "กล่องอเนกประสงค์" มีหลายแบบ ไม่ใช่แบบเดียว

พูดว่า "NoSQL" เฉยๆ ยังกว้างเกินไป — ในทางปฏิบัติแบ่งเป็น 4 กลุ่มหลัก ที่แต่ละกลุ่มเหมาะกับงานคนละแบบ:

- <mark class="hl-term">Key-Value</mark> (Redis, DynamoDB) — เหมือนตู้ล็อกเกอร์ที่มีแค่เลขล็อกเกอร์กับของข้างใน ไม่รู้เนื้อหาข้างในเลย เร็วที่สุดเพราะ query ง่ายสุด (ขอด้วย key เดียว)
- <mark class="hl-term">Document</mark> (MongoDB) — เหมือนแฟ้มที่แต่ละแฟ้มมีโครงสร้างยืดหยุ่นของตัวเอง (เก็บเป็น JSON) query ได้ลึกกว่า key-value เพราะดูเนื้อหาข้างในเอกสารได้
- <mark class="hl-term">Column-Family / Wide-Column</mark> (Cassandra) — เหมาะกับข้อมูลที่เขียนถี่มหาศาลระดับ IoT sensor หรือ time-series เพราะออกแบบมาให้ scale การเขียนแนวนอนได้ดีเป็นพิเศษ
- <mark class="hl-term">Graph</mark> (Neo4j) — เหมาะกับข้อมูลที่ความสัมพันธ์สำคัญกว่าตัวข้อมูลเอง (เช่น social network "เพื่อนของเพื่อนของเพื่อน") ซึ่ง SQL ทำ JOIN ซ้อนกันหลายชั้นจะช้ามาก แต่ graph database เดินตามเส้นความสัมพันธ์ได้เร็วโดยธรรมชาติ

<mark class="hl-insight">คำว่า NoSQL ที่ยอม eventual consistency แลกความเร็ว/scale มีชื่อโมเดลทางการว่า BASE (Basically Available, Soft state, Eventual consistency) — ตรงข้ามกับ ACID ของ SQL ที่ยึด consistency เป็นหลักเสมอ</mark> ไม่ใช่ทุก NoSQL ต้องยอม BASE เสมอไป (บางตัวเลือก consistency ได้ปรับได้) แต่นี่คือแนวคิดตั้งต้นที่ NoSQL ส่วนใหญ่ถือกัน

> คำถามสัมภาษณ์: "ถ้าจะเก็บข้อมูล social network (เพื่อน, follower) ควรใช้ database แบบไหน" — ถ้าความสัมพันธ์ซับซ้อนหลายชั้น (เพื่อนของเพื่อน, แนะนำเพื่อนร่วมกัน) Graph Database เหมาะที่สุดเพราะเดินตามเส้นความสัมพันธ์ได้เร็วโดยไม่ต้อง JOIN ซ้อนกันหลายชั้นแบบ SQL แต่ถ้าความสัมพันธ์เรียบง่าย (แค่ user follow user) เก็บเป็นตาราง SQL ธรรมดาหรือ document ก็เพียงพอ ไม่จำเป็นต้องใช้ graph database เสมอไป
