พอเข้าใจว่า stock คือ "สิ่งที่สะสม วัดได้ทันทีตอนหยุดเวลาดู" แล้ว ทีนี้ลองมองไปรอบๆ งานที่ทำอยู่ทุกวัน — คุณจะเริ่มเห็น stock ซ่อนอยู่แทบทุกที่ ทั้งที่ก่อนหน้านี้อาจไม่เคยคิดว่ามันคือ "stock" มาก่อนเลย นี่คือพลังของคำศัพท์ที่แม่นยำ — พอมีคำเรียก คุณจะเริ่ม "มองเห็น" สิ่งที่มองไม่เห็นมาก่อน

## Technical Debt คือ Stock

Technical debt ไม่ใช่แค่คำเปรียบเปรยลอยๆ มันมีโครงสร้าง stock/flow จริงจังไม่ต่างจากอ่างอาบน้ำเลย:

- **Stock** = ปริมาณ technical debt ที่สะสมอยู่ในโค้ดตอนนี้
- **Inflow** = ทางลัดที่ทีมเลือกใช้ทุกครั้งที่ deadline บีบ (skip test, hardcode ค่า, copy-paste แทนที่จะ abstract)
- **Outflow** = เวลาที่ทีมจัดสรรไป refactor คืนหนี้นั้น

## Queue คือ Stock ที่วิศวกรระบบคุ้นเคยที่สุด

ระบบ web server ที่มี request เข้ามาไม่เท่ากันตลอดเวลา คือ stock/flow ที่วิศวกร backend เจอทุกวันโดยไม่รู้ตัวว่ากำลังใช้กรอบคิดนี้อยู่:

- **Stock** = จำนวน request ที่ค้างอยู่ในคิว รอประมวลผล
- **Inflow** = อัตราที่ request เข้ามาใหม่ (requests/second)
- **Outflow** = อัตราที่ server ประมวลผล request เสร็จ (throughput)

ถ้า inflow > outflow ต่อเนื่อง คิวจะยาวขึ้นเรื่อยๆ จนสุดท้าย memory เต็มหรือ latency พุ่งจนผู้ใช้ทนไม่ไหว — นี่คือเหตุผลเชิงโครงสร้างเบื้องหลัง rate limiting, circuit breaker, autoscaling ทั้งหมดที่เรียนใน track System Design: **ทุกกลไกเหล่านั้นคือการควบคุม flow เพื่อไม่ให้ stock (คิว) วิ่งหนีจนควบคุมไม่ได้** — พอมองผ่านเลนส์ stock/flow เครื่องมือที่เคยดูเป็นเรื่องเทคนิคแยกกันคนละเรื่อง จะเห็นเป็นภาพเดียวกันหมดทันที

## Cash และ Users ก็เป็น Stock เช่นกัน

| Stock | Inflow | Outflow | สังเกตอะไรได้บ้าง |
|---|---|---|---|
| เงินสดในบริษัท (Cash/Runway) | รายได้, เงินระดมทุน | ค่าใช้จ่ายดำเนินงาน (burn rate) | "Runway" ที่สตาร์ทอัพพูดถึง คือประมาณการว่า stock จะถึงศูนย์เมื่อไหร่ถ้า inflow/outflow คงเดิม |
| ผู้ใช้งาน (Active Users) | ผู้ใช้ใหม่ที่สมัคร (acquisition) | ผู้ใช้ที่เลิกใช้ (churn) | Growth ที่ยั่งยืนต้องดูทั้งสองฝั่ง ไม่ใช่ทุ่มงบดึง inflow อย่างเดียวโดยไม่แก้ churn |
| Backlog งาน (Product/Engineering) | feature request/bug ใหม่ที่เข้ามา | งานที่ทีมปิดจบได้ | Backlog ที่ "ไม่มีวันหมด" มักแปลว่า inflow ถูกปล่อยให้เปิดกว้างเกินไปเทียบกับ outflow capacity ของทีม |

จุดที่น่าสนใจคือ "acquisition" (การหาลูกค้าใหม่) มักได้รับความสนใจและงบประมาณมากกว่า "retention" (การรักษาลูกค้าเดิม ลด churn) เสมอ ทั้งที่จากมุม stock/flow แล้วทั้งสองฝั่งมีน้ำหนักเท่ากันในการกำหนดว่า stock (จำนวนผู้ใช้) จะโตหรือหด — บริษัทที่ acquisition แรงมากแต่ churn ก็แรงพอกัน จะเห็น user count นิ่งอยู่ที่เดิมทั้งที่เผาเงินการตลาดไปมหาศาล เป็นภาพเดียวกับตัวอย่างบริษัท 200 คนที่ turnover สูงในหัวข้อก่อนหน้าเป๊ะ

## ทำไมการมองแบบนี้เปลี่ยนวิธีแก้ปัญหา

พอรู้ว่าอะไรคือ stock อะไรคือ flow ของระบบที่กำลังดูแลอยู่ คำถามเวลาเจอปัญหาจะเปลี่ยนจาก "จะแก้ปัญหานี้ยังไง" (คำถามกว้างเกินไป) เป็นคำถามที่จำกัดขอบเขตชัดเจนกว่ามาก: **"stock ตัวนี้ผิดปกติเพราะ inflow มากไป, outflow น้อยไป, หรือทั้งสองอย่าง"** — คำถามแบบนี้พาไปสู่ทางแก้ที่ตรงจุดกว่าการเดาสุ่มมาก

โมดูลถัดไปในหัวข้อสุดท้ายของโมดูลนี้จะพาไปดูตัวแปรที่ทำให้เรื่องนี้ซับซ้อนขึ้นอีกขั้น: **delay** — ทำไม flow ที่ดูเหมือนปรับได้ทันทีในทางทฤษฎี ถึงมักไม่ส่งผลทันทีในโลกจริง
