ลองนึกภาพเสียงตามสายในโรงเรียน — ผู้อำนวยการประกาศครั้งเดียวผ่านไมค์ ทุกห้องเรียนที่เปิดลำโพงอยู่ได้ยินพร้อมกันหมด ไม่ต้องเดินไปบอกทีละห้อง และแต่ละห้องก็ทำอะไรกับประกาศนั้นไม่เหมือนกัน — ห้องหนึ่งอาจส่งตัวแทนไปที่ประชุม อีกห้องอาจแค่จดบันทึกไว้ ผู้อำนวยการไม่ต้องรู้เลยด้วยซ้ำว่าห้องไหนจะทำอะไรกับประกาศนั้น

Message Queue (บทที่แล้ว) มีสมมติฐานว่า **1 บัตรคิวควรถูกทำโดยบาริสต้าแค่ 1 คน** (พอคนหนึ่งดึงไปทำ คนอื่นดึงซ้ำไม่ได้) แต่บางสถานการณ์ต้องการให้ **ประกาศเดียวกันไปถึงหลายฝ่ายพร้อมกัน** — นี่คือที่มาของ <mark class="hl-term">Pub/Sub</mark>

## Queue vs Pub/Sub

```mermaid

    subgraph Queue["Message Queue (บัตรคิว)"]

        Q --> CQ1["Consumer 1\n(ได้งานไปทำคนเดียว)"]
    end
    subgraph PubSub["Pub/Sub (เสียงตามสาย)"]
        PP["Publisher (ผอ.)"] --> Topic["Topic (ไมค์ประกาศ)"]
        Topic --> S1["ห้อง A (Email Service)"]
        Topic --> S2["ห้อง B (Analytics)"]
        Topic --> S3["ห้อง C (Notification)"]
    end
```

<mark class="hl-insight">ความต่างสำคัญ: บัตรคิวถูกบาริสต้าคนใดคนหนึ่งหยิบไปแล้วหายจากคิว (คนอื่นไม่เห็นอีก) แต่ประกาศเสียงตามสายถูกส่งไปหาทุกห้องที่เปิดลำโพงรับฟังพร้อมกัน</mark> แต่ละห้องทำงานของตัวเองอย่างอิสระ

## ลองดูการกระจายเสียงจริง

ลองกด Publish แล้วสลับโหมดดู — ถ้าประกาศทีละห้อง (sequential) ต้องรอห้องแรกจัดการเสร็จก่อนถึงจะประกาศห้องถัดไป เทียบกับประกาศพร้อมกันทุกห้องในทีเดียว (parallel) ดูว่าเวลารวมต่างกันแค่ไหน

## ตัวอย่าง: User สมัครสมาชิกใหม่

ประกาศเดียว "`user.registered`" อาจต้องกระตุ้นหลายระบบพร้อมกัน:
- ส่งอีเมลต้อนรับ
- บันทึก analytics event
- สร้าง default settings ให้ user
- แจ้งทีม marketing (ถ้าเป็น business account)

ถ้าเขียนโค้ดเรียกทุกระบบตรงๆ ใน function เดียว (เหมือนผู้อำนวยการต้องเดินไปบอกทีละห้องเอง) โค้ดจะพันกันยุ่งเหยิง และถ้าอนาคตมีระบบที่ 5 มาสนใจ ต้องแก้โค้ดจุดเดิมซ้ำอีก — Pub/Sub แก้ปัญหานี้: **publisher แค่ประกาศผ่านไมค์** ไม่ต้องรู้จักหรือสนใจว่าใครฟังอยู่บ้าง ระบบใหม่แค่ "เปิดลำโพง" (subscribe topic เดิม) เพิ่ม ไม่ต้องแก้โค้ดผู้ประกาศเลย

> ตัวอย่างจริง: Kafka, Google Pub/Sub, AWS SNS — นี่คือรากฐานของ **Event-Driven Architecture** (หัวข้อถัดไป)

## ขั้นสูง: ห้องเรียนที่ฟังช้ากว่าเพื่อน จะเกิดอะไรขึ้น (Consumer Lag)

Pub/Sub ต่างจาก Message Queue อีกจุดที่ไม่ได้พูดถึงตรงๆ — <mark class="hl-insight">แต่ละ subscriber (ห้องเรียน) จำตำแหน่งที่ตัวเอง "ฟังไปถึงไหนแล้ว" ของตัวเองแยกกัน (เรียกว่า offset) ทำให้ห้องที่ฟังช้ากว่าไม่ไปบล็อกห้องที่ฟังเร็วกว่าเลย</mark> แต่ก็มีผลข้างเคียง: ถ้าห้องหนึ่งประมวลผลช้ากว่าห้องอื่นเรื่อยๆ (เช่น service นั้น overload หรือกำลังแก้บั๊ก) มันจะ**ล้าหลังมากขึ้นสะสมไปเรื่อยๆ** เรียกว่า <mark class="hl-term">Consumer Lag</mark>

ปัญหาที่ตามมาคือ <mark class="hl-warning">ประกาศส่วนใหญ่ไม่ได้เก็บไว้ตลอดไป — มี retention period จำกัด (เช่น Kafka default เก็บ 7 วัน) ถ้า consumer ล้าหลังจนเกินช่วง retention ข้อความที่ยังไม่ทันอ่านจะถูกลบทิ้งไปเลยก่อนที่ consumer จะได้อ่าน</mark> ต่างจาก Message Queue ที่ข้อความมักอยู่ในคิวจนกว่าจะมีคนมา ack (ไม่หายเองตามเวลา) — นี่คือเหตุผลที่ทีมต้อง monitor consumer lag อย่างใกล้ชิด ถ้า lag เพิ่มขึ้นเรื่อยๆ ไม่หยุด ต้องเพิ่มกำลังประมวลผล (scale consumer) ก่อนที่ข้อมูลจะหายจริง

> คำถามสัมภาษณ์: "Consumer Lag คืออะไร ทำไมต้องจับตาดู" — คือระยะห่างระหว่างข้อความล่าสุดที่ publish กับตำแหน่งที่ consumer ตัวหนึ่งอ่านไปถึง ถ้า lag เพิ่มขึ้นต่อเนื่องแปลว่า consumer ประมวลผลไม่ทันปริมาณข้อความที่เข้ามา อันตรายเพราะ topic ส่วนใหญ่มี retention period จำกัด ถ้า lag มากเกินช่วง retention ข้อความจะถูกลบไปก่อนที่ consumer จะได้อ่านเลย ต้อง scale consumer หรือหาสาเหตุที่ทำให้ประมวลผลช้าก่อนที่ข้อมูลจะสูญหายจริง
