ลองนึกภาพร้านกาแฟตอนเช้าที่คนแน่นมาก — แทนที่จะให้ทุกคนยืนออกันหน้าเคาน์เตอร์รอดูว่ากาแฟตัวเองเสร็จหรือยัง ร้านให้**บัตรคิว**ไปแทน คุณกดบัตร วางไว้กับตัว แล้วไปนั่งรอที่โต๊ะได้เลย บาริสต้าชงกาแฟตามลำดับบัตรคิว เสร็จแล้วเรียกเลขคิว — คุณไม่ต้องยืนจ้องเคาน์เตอร์ตลอดเวลา

**Message Queue** คือโครงสร้างข้อมูลกลาง (มักเป็น FIFO - First In, First Out - เข้าก่อนออกก่อน เหมือนบัตรคิว) ที่ producer (คนกดบัตรคิว) ส่งงานเข้าไปเก็บไว้ แล้ว consumer (บาริสต้า) ค่อยๆ ดึงออกไปทำทีละงานตามลำดับ

## ทำไม Queue ถึงช่วยเรื่อง Scale

Queue ทำหน้าที่เป็น<mark class="hl-insight">บัฟเฟอร์ระหว่างฝั่งสั่งงาน (producer) กับฝั่งทำงาน (consumer) — ทั้งสองฝั่งไม่ต้องเร็วเท่ากัน</mark> เหมือนบัตรคิวที่ทำให้คนสั่งกาแฟกับบาริสต้าไม่ต้องซิงค์จังหวะกันแบบเรียลไทม์:

- Producer (คนสั่ง) กดบัตรคิวเร็วแค่ไหนก็ได้ ไม่ต้องรอบาริสต้าทำเสร็จก่อน
- Consumer (บาริสต้า) ทำงานตามจังหวะของตัวเอง ถ้าคนแน่นเกิน**เพิ่มบาริสต้า**ได้ (horizontal scaling แบบเดียวกับโมดูล Scalability แต่ใช้กับ "งาน" แทน "request")
- ถ้าบาริสต้าคนหนึ่งลาป่วยกะทันหัน บัตรคิวไม่หาย — ยังรออยู่ในคิว พอมีบาริสต้าคนอื่นมาทำต่อได้

## At-least-once — บัตรคิวอาจถูกเรียกซ้ำได้

จุดที่ทำให้ queue ซับซ้อนกว่าที่คิด: ถ้าบาริสต้าดึงบัตรคิวไปทำแล้ว**เดินหายไปกลางคัน**ก่อนบอกร้านว่า "ทำเสร็จแล้ว" บัตรคิวนั้นควรถูกส่งให้บาริสต้าคนอื่นทำใหม่ — นี่คือ <mark class="hl-term">at-least-once delivery</mark> (อาจทำงานซ้ำได้ถ้าบาริสต้าคนเดิมจริงๆ ทำเสร็จแต่แค่ลืมบอก)

```mermaid
flowchart LR
    Q["Queue (คิวบัตร)"] -->|"1 ดึงบัตรคิว (ยังไม่ลบออก)"| C["Consumer (บาริสต้า)"]
    C -->|"2 ชงเสร็จ"| ACK["3 กดยืนยันว่าทำเสร็จ (ACK)"]
    ACK -->|"4 Queue ลบบัตรคิวออกจริง"| Q
    C -.->|"ถ้าเดินหายไปก่อนกด ACK"| Retry["Queue ส่งบัตรคิวเดิมให้บาริสต้าคนอื่นทำใหม่"]
```

เพราะแบบนี้ <mark class="hl-warning">งานที่ทำผ่าน queue ควรออกแบบให้ทำซ้ำแล้วผลลัพธ์เหมือนเดิม (idempotent)</mark> เช่น "ตั้งสถานะเป็น paid" ทำซ้ำกี่ครั้งก็ยังเป็น paid เหมือนชงกาแฟแก้วเดิมซ้ำไม่เสียหาย ไม่ใช่ "บวกเงินเพิ่ม" ที่ถ้าชงซ้ำ (ทำงานซ้ำ) จะผิดพลาดทันที (ลูกค้าได้กาแฟสองแก้วทั้งที่สั่งแค่แก้วเดียว)

> ตัวอย่างจริง: RabbitMQ, AWS SQS, Redis Streams — ต่างกันในรายละเอียด แต่หลักการ "กดบัตรคิว → เข้าคิว → บาริสต้าดึงไปทำทีละใบ" เหมือนกันหมด

## ขั้นสูง: Dual Write Problem — บันทึกสมุดสำเร็จ แต่บัตรคิวไม่ออก

ปัญหาที่ตำราเบื้องต้นมักข้ามไป: ระบบจริงต้อง**บันทึกออเดอร์ลง database** และ**ส่ง message เข้า queue** — สองการกระทำนี้เป็นการเขียนข้อมูลคนละที่กัน (dual write) <mark class="hl-warning">ถ้าระบบล่มกลางทางระหว่างสองจังหวะนี้ (เช่น บันทึกออเดอร์สำเร็จ แต่ไฟดับก่อนส่ง message เข้า queue) ออเดอร์จะถูกบันทึกไว้ แต่ไม่มีใครถูกแจ้งให้ไปทำต่อเลย</mark> เหมือนร้านบันทึกออเดอร์ลงสมุดเรียบร้อย แต่เครื่องพิมพ์บัตรคิวดับพอดี — ลูกค้าเสียเงินแต่ไม่มีใครมาชงกาแฟให้

```mermaid
flowchart LR
    A["บันทึกออเดอร์ลง DB"] -->|"สำเร็จ"| B{"ไฟดับตรงนี้ได้ไหม"}
    B -->|"ดับก่อนส่ง message"| C["Queue ไม่รู้เรื่องเลย — ออเดอร์ตกหล่น"]
    B -->|"ไม่ดับ"| D["ส่ง message เข้า Queue สำเร็จ"]
```

ทางแก้มาตรฐานคือ <mark class="hl-term">Transactional Outbox Pattern</mark> — แทนที่จะส่ง message เข้า queue ตรงๆ (การเขียนที่สองแยกจาก DB) ให้เขียนบันทึก "รอส่ง" ลงตาราง `outbox` **ในธุรกรรมเดียวกัน (atomic transaction)** กับการบันทึกออเดอร์เลย — เพราะเป็น DB transaction เดียวกัน จะสำเร็จทั้งคู่หรือไม่สำเร็จทั้งคู่เท่านั้น ไม่มีทางสำเร็จแค่ครึ่งเดียว จากนั้นมี process แยกต่างหาก (relay) คอยอ่านตาราง `outbox` เป็นระยะแล้วค่อยส่งเข้า queue จริง — ถ้าส่งไม่สำเร็จ ลองใหม่ได้เรื่อยๆ เพราะบันทึกยังอยู่ในตาราง ไม่ได้หายไปพร้อมกับความล่ม

> คำถามสัมภาษณ์: "ทำไมไม่ publish event ตรงๆ หลัง commit DB เสร็จเลย" — เพราะช่วงเวลาระหว่าง "DB commit สำเร็จ" กับ "publish event สำเร็จ" คือช่องโหว่ที่ระบบล่มได้เสมอ (network, process crash) — Transactional Outbox ปิดช่องโหว่นี้โดยทำให้การบันทึก "ต้องส่ง event นี้" เป็นส่วนหนึ่งของ transaction เดียวกันกับข้อมูลจริง ไม่ใช่ก้าวที่สองที่แยกออกไปเสี่ยงล่มเดี่ยวๆ
