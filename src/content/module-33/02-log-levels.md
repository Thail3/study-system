ลองนึกภาพเจ้าหน้าที่รักษาความปลอดภัยที่จดบันทึกทุกอย่างที่เห็น ตั้งแต่ "นกบินผ่าน" ไปจนถึง "มีคนบุกรุก" — ถ้าจดทุกอย่างระดับเดียวกันหมด รายงานจะยาวจนหาเรื่องสำคัญไม่เจอ ระบบ logging จึงต้องมี**ระดับความสำคัญ** เพื่อแยกว่าอะไรควรอ่านทันที อะไรเก็บไว้เผื่อสืบสวนทีหลัง เรียกว่า <mark class="hl-term">**Log Level**</mark>

## ลำดับ Log Level มาตรฐาน

```mermaid
flowchart LR
    D["DEBUG\nรายละเอียดตอน dev"] --> I["INFO\nเหตุการณ์ปกติที่ควรรู้"]
    I --> W["WARN\nผิดปกติแต่ยังทำงานต่อได้"]
    W --> E["ERROR\nงานนี้ล้มเหลว"]
    E --> F["FATAL\nระบบทำงานต่อไม่ได้"]
```

| Level | ใช้เมื่อไหร่ | ตัวอย่าง |
|---|---|---|
| **DEBUG** | รายละเอียดสำหรับ debug ตอน dev เท่านั้น | ค่าตัวแปรระหว่างคำนวณ, SQL query ที่รันจริง |
| **INFO** | เหตุการณ์ปกติที่ควรบันทึกไว้ | "order สร้างสำเร็จ", "user login" |
| **WARN** | ผิดปกติแต่ระบบยังทำงานต่อได้ | retry สำเร็จหลังพยายามครั้งที่ 2, ใช้ fallback config |
| **ERROR** | งานนี้ล้มเหลว ต้องมีคนรู้ | payment ล้มเหลว, ต่อ database ไม่ได้ |
| **FATAL** | ระบบทำงานต่อไปไม่ได้เลย | ไม่สามารถโหลด config ตอน start ได้ ต้องปิดโปรแกรม |

## ต้นทุนของการ Log มากเกินไป

<mark class="hl-warning">Log ทุกบรรทัดมีต้นทุนจริง — ทั้งพื้นที่เก็บ, ค่า ingest ของระบบ log aggregation (มักคิดตามปริมาณข้อมูล), และ**performance overhead**ที่ตัว application เอง (I/O การเขียน log บ่อยเกินไปแย่งเวลา CPU ที่ควรใช้ตอบ request) ทีมที่ตั้ง production log level เป็น DEBUG ทิ้งไว้ มักเจอบิล log aggregation พุ่งสูงผิดปกติ โดยที่ log ส่วนใหญ่ไม่มีใครเปิดดูเลยด้วยซ้ำ</mark>

แนวทางที่ใช้กันทั่วไป: <mark class="hl-insight">production ตั้ง log level ไว้ที่ INFO ขึ้นไปเป็นค่าเริ่มต้น (ไม่เปิด DEBUG) แล้วเปิด DEBUG ชั่วคราวเฉพาะตอนสืบสวนปัญหาเท่านั้น — บาง framework รองรับปรับ log level แบบ dynamic ได้โดยไม่ต้อง deploy ใหม่ ซึ่งมีประโยชน์มากตอน incident</mark>

## Sampling — เมื่อ Log เยอะเกินจะเก็บครบทุกบรรทัด

ระบบที่มี traffic สูงมาก (เช่น INFO log ทุก request ของ service ที่รับ 100,000 req/sec) เก็บ log ทุกบรรทัดไม่ไหวทั้งพื้นที่และค่าใช้จ่าย — ใช้เทคนิค <mark class="hl-term">Log Sampling</mark> คือ**เก็บแค่บางส่วน**ของ log ที่ถือว่าไม่วิกฤต (เช่น เก็บ INFO log แค่ 1% แบบสุ่ม) แต่**เก็บ ERROR/WARN ทุกบรรทัดเสมอ 100%** เพราะเหตุการณ์ผิดปกติมีน้อยกว่ามากและสำคัญกว่าที่จะไม่พลาด

| Level | Sample Rate ทั่วไป | เหตุผล |
|---|---|---|
| DEBUG | ปิดใน production | รายละเอียดเกินไป ไม่คุ้มต้นทุน |
| INFO | อาจ sample 1-10% ถ้า traffic สูงมาก | เหตุการณ์ปกติเยอะ ไม่จำเป็นต้องครบทุกบรรทัด |
| WARN/ERROR/FATAL | 100% เสมอ | เหตุการณ์ผิดปกติ พลาดไม่ได้ |

> คำถามสัมภาษณ์: "service รับ 100,000 request/sec แต่ต้อง log ทุก request จะทำยังไงไม่ให้ค่าใช้จ่าย log พุ่งเกินจริง" — คำตอบที่ดีคือใช้ log sampling: เก็บ INFO log แบบสุ่มเป็น % เล็กๆ พอให้เห็นภาพรวม แต่เก็บ WARN/ERROR/FATAL ทุกบรรทัด 100% เสมอ เพราะเหตุการณ์ผิดปกติมีปริมาณน้อยกว่ามากและพลาดไม่ได้ ต่างจาก INFO ที่เป็นเหตุการณ์ปกติจำนวนมหาศาล
