ลองนึกภาพว่าคุณได้รับมรดกเป็นบ้านเก่าหลังหนึ่งจากญาติที่เพิ่งเสียชีวิต บ้านหลังนี้ถูกต่อเติมมาหลายรอบตลอด 20 ปี — ต่อครัวใหม่ปีนี้ เพิ่มห้องนอนชั้นบนปีนั้น เดินท่อประปาใหม่อีกรอบตอนน้ำรั่วเมื่อสามปีก่อน แต่ไม่มีใบอนุญาตต่อเติมสักใบ ไม่มีพิมพ์เขียวอัปเดตสักแผ่นเหลืออยู่เลย มีแค่ตัวบ้านจริงที่ยืนอยู่ตรงหน้า กับเพื่อนบ้านคนเดียวที่จำได้ลางๆ ว่า "ท่อแก๊สน่าจะเดินผ่านใต้ห้องครัว" แต่เพื่อนบ้านคนนั้นกำลังจะย้ายไปอยู่ต่างจังหวัดในอีกสองเดือน

คุณต้องอยู่ในบ้านหลังนี้ทันที ไม่มีเวลาหยุดพักเพื่อรื้อสร้างใหม่ทั้งหมด และก่อนจะเจาะผนังติดแอร์เครื่องใหม่สักตัว คุณต้องรู้ก่อนว่าจะไปโดนสายไฟหรือท่อน้ำที่ซ่อนอยู่ตรงไหนหรือเปล่า สถาปนิกมืออาชีพจะไม่เริ่มจากการถามเพื่อนบ้านทุกคนแล้วเอาคำตอบมาปะติดปะต่อ (เพราะความจำคนคลาดเคลื่อนและตกหล่นได้เสมอ) แต่จะสำรวจตัวบ้านจริงอย่างเป็นระบบ เคาะผนังฟังเสียงกลวง เปิดฝ้าเพดานดูสายไฟจริง แล้ววาดพิมพ์เขียวขึ้นมาใหม่จากสิ่งที่เห็นจริงต่อหน้า

สถานการณ์เดียวกันนี้เกิดขึ้นทุกวันในทีมวิศวกรรมซอฟต์แวร์ — วิศวกรใหม่ (หรือทีมทั้งทีมที่ถูกโอนย้ายมาจากการปรับโครงสร้างองค์กร) ต้องเข้ามาดูแลระบบ production ที่ไม่มีเอกสารสถาปัตยกรรมเหลืออยู่เลย ไม่มี diagram ไม่มี ADR มีแค่โค้ดที่รันอยู่จริงกับความรู้ที่ฝังอยู่ในหัวคนไม่กี่คนที่กำลังจะลาออก นี่คือปัญหาคลาสสิกที่เรียกว่า <mark class="hl-term">**Undocumented Legacy System**</mark> และทางออกไม่ใช่การรีบถามคนเก่าให้ครบทุกคนก่อนที่พวกเขาจะไป แต่คือการทำสิ่งที่สถาปนิกบ้านทำ — ใช้ระบบจริงที่รันอยู่เป็น source of truth

## Requirement คร่าวๆ

- ทีมใหม่ต้องเข้าใจระบบเพียงพอที่จะแก้บั๊กและส่ง feature เล็กๆ ได้ภายในไม่กี่สัปดาห์ โดยไม่รอให้ "มีคนอธิบายให้ฟังครบทุกจุด" ก่อน
- ห้ามหยุดระบบ production เพื่อสำรวจ — ต้องเรียนรู้ไปพร้อมกับระบบที่ยังให้บริการผู้ใช้จริงอยู่ตลอดเวลา
- tribal knowledge ของทีมเดิมกำลังจะหายไปพร้อมกับคนที่ลาออก/ย้ายทีมภายใน 1-2 เดือน ต้องรีบดึงเฉพาะส่วนที่ "ตัวระบบเองบอกไม่ได้" ออกมาก่อนคนกลุ่มนี้จะไป
- ทุกอย่างที่ทีมใหม่เรียนรู้มา ต้องถูกบันทึกเป็นเอกสารที่คนถัดไปอ่านต่อได้ ไม่ใช่ปล่อยให้กลับไปเป็นความรู้ปากเปล่าเหมือนเดิมอีกรอบ
- ห้ามเปลี่ยนโครงสร้างระบบใหญ่ๆ จนกว่าจะเข้าใจภาพจริงพอสมควร — เปลี่ยนแปลงโดยไม่รู้ blast radius คือความเสี่ยงที่ยอมรับไม่ได้กับระบบที่มีผู้ใช้จริงอยู่แล้ว

## ใช้ระบบจริงเป็น Source of Truth: Reverse-Engineer C4 Container Diagram

โมดูล 14 (Architecture Documentation & Views) สอนไว้ว่า C4 Model ซูมจากภาพกว้างไปแคบทีละชั้น — Context, Container, Component, Code แต่สำหรับระบบไร้เอกสาร จุดเริ่มต้นที่คุ้มค่าที่สุดไม่ใช่ Context (เพราะรู้อยู่แล้วคร่าวๆ ว่าธุรกิจนี้ทำอะไร) แต่คือ **Container** — เพราะคำถามที่ตอบไม่ได้จริงๆ ตอนนี้คือ "มีกี่ service กันแน่ที่รันอยู่ ใครคุยกับใคร" คำถามนี้ต้องตอบด้วยการอ่านของจริง ไม่ใช่ถามคน

วิธีทำจริงคือไล่ตรวจ infra ที่รันอยู่ — ดู deployment config, connection string ที่ hardcode ในโค้ด, crontab บน server, consumer ที่ subscribe queue อยู่จริง แล้วค่อยเอาสิ่งที่คนเดิมยังจำได้มาช่วยยืนยันหรือเติมช่องว่างทีหลัง ไม่ใช่ใช้เป็นแหล่งข้อมูลหลักตั้งแต่แรก <mark class="hl-insight">ระบบที่รันอยู่จริงโกหกไม่ได้ ต่างจากความทรงจำของคนที่คลาดเคลื่อนได้ตลอดเวลาโดยที่เจ้าตัวไม่รู้ตัวด้วยซ้ำ</mark>

```mermaid
C4Container
    title Legacy Order Platform (สร้างใหม่จากการสำรวจระบบจริง)

    Person(newEngineer, "วิศวกรใหม่", "กำลังศึกษาระบบเพื่อรับช่วงดูแล")

    System_Boundary(legacy, "Legacy Order Platform") {
        Container(monolith, "Order Monolith", "PHP 5 (legacy)", "แอปหลักที่พบว่ายังรับ traffic จริงอยู่ราว 80%")
        Container(cronWorker, "Nightly Reconciliation Job", "Cron + Python script", "พบจาก crontab บน server จริง ไม่มีในเอกสารใดๆ เลย")
        Container(hiddenConsumer, "Undocumented Queue Consumer", "Node.js worker", "พบจากการไล่ log ว่ามีตัวไปดึงข้อความจาก queue เดิม")
        ContainerDb(mainDb, "Orders DB", "MySQL 5.7", "ยืนยันจาก connection string ที่ hardcode อยู่ในโค้ด")
    }

    System_Ext(legacyQueue, "Message Queue", "RabbitMQ เวอร์ชันเก่าที่ยังรันอยู่บน VM ตัวเดิม")

    Rel(newEngineer, monolith, "อ่านโค้ด/log เพื่อทำความเข้าใจ")
    Rel(monolith, mainDb, "อ่าน/เขียนข้อมูล order")
    Rel(cronWorker, mainDb, "รันทุกเที่ยงคืน กระทบยอดข้อมูล")
    Rel(monolith, legacyQueue, "ส่งข้อความเมื่อ order เปลี่ยนสถานะ")
    Rel(hiddenConsumer, legacyQueue, "ดึงข้อความไปประมวลผลต่อ (ไม่มีใครในทีมจำได้ว่าใครเขียน)")
```

สิ่งที่มักเจอระหว่างสำรวจคือของจริงไม่ตรงกับคำบอกเล่าของคนในทีมเลย เพราะระบบที่ไม่มีใครคอยรักษาวินัยด้านสถาปัตยกรรมมักถูกกัดกร่อนไปทีละจุดตามการแก้ปัญหาเฉพาะหน้า — ปรากฏการณ์ที่โมดูล 21 (Evolutionary Architecture & Anti-pattern) เรียกว่า architecture erosion เอกสารที่หายไปกับสถาปัตยกรรมที่เสื่อมสภาพจึงมักเป็นปัญหาคู่แฝดที่มาด้วยกันเสมอ แต่เคสนี้ยังโฟกัสที่การสร้างเอกสารกลับคืนมาก่อน ไม่ใช่การแก้ erosion โดยตรง

## จัดสิ่งที่ค้นพบเข้า 4+1 View ให้ตรงคำถามที่จะโดนถาม

พอมี Container diagram แล้ว ข้อมูลที่เก็บมาระหว่างสำรวจจะกระจัดกระจาย — ต้องใช้ **4+1 View Model** (โมดูล 14) จัดเข้ากล่องให้ถูกที่ ไม่ใช่โยนทุกอย่างลง diagram เดียวจนอ่านไม่รู้เรื่อง

- **Logical View** — ระหว่างไล่โค้ด Order Monolith จะเจอ concept ทางธุรกิจที่ไม่มีใครเขียนอธิบายไว้ เช่น สถานะ order ที่ซ่อนอยู่ในคอลัมน์ `status_code` เป็นตัวเลข ต้องไล่ enum ในโค้ดมาสร้างเป็น domain model ใหม่ทั้งหมด แล้วบันทึกไว้เป็น Logical View
- **Physical/Deployment View** — บันทึกว่า monolith รันอยู่บน VM ตัวไหน cron job ถูก schedule ด้วยอะไร queue consumer deploy แยกจากตัวหลักหรือเปล่า ข้อมูลนี้ต้องดึงจาก infra จริง ไม่ใช่จากรูปเก่าใน slide ที่อาจล้าสมัยไปหลายปีแล้ว
- **Process View** — ต้องสังเกตพฤติกรรม runtime ภายใต้โหลดจริง เช่น ช่วงที่ cron job รันตอนเที่ยงคืนพร้อมกับมี queue consumer ประมวลผลอยู่ด้วย ทำให้ DB connection พุ่งสูงจนบางครั้ง request ปกติช้าลง — พฤติกรรมแบบนี้ไม่มีทางรู้ได้จากการอ่านโค้ดเฉยๆ ต้องสังเกตของจริงตอนระบบทำงาน

## ตารางเปรียบเทียบ Trade-off: ถามคนเดิม vs สำรวจระบบจริง

| ประเด็น | ถามคนในทีมเดิม (tribal knowledge) | สำรวจระบบจริง (code/infra archaeology) |
|---|---|---|
| ความเร็วในช่วงแรก | เร็ว — ถามคำถามตรงๆ ได้คำตอบทันที | ช้ากว่า — ต้องไล่โค้ด, log, config เอง |
| ความแม่นยำ | เสี่ยงคลาดเคลื่อนหรือคนจำผิดโดยไม่รู้ตัว | แม่นยำเท่าที่ระบบจริงเป็น ไม่มีอคติของความทรงจำ |
| อายุของข้อมูล | หมดอายุทันทีที่คนคนนั้นลาออก | คงอยู่ตราบใดที่ระบบยังรันอยู่ |
| ครอบคลุมมุมที่คนลืม | ครอบคลุมไม่ได้เลยถ้าไม่มีใครจำ | ครอบคลุมทุกจุดที่ระบบสัมผัส แม้ไม่มีใครจำได้ |
| เหมาะกับ | ยืนยัน "ทำไม" ถึงตัดสินใจแบบนี้ (เจตนา) | หา "อะไร" ที่รันอยู่จริง (โครงสร้าง) |

## เขียน ADR แรก: วางวินัยที่ระบบนี้ไม่เคยมี

พอเข้าใจระบบพอจะลงมือแก้จริงได้ครั้งแรก — เช่น ตัดสินใจย้าย Undocumented Queue Consumer ออกจาก VM เดิมไปรันเป็น container แยก — จุดนี้คือโอกาสสำคัญที่สุดในการวาง<mark class="hl-warning">วินัยที่ระบบเดิมไม่เคยมี</mark> ถ้าทำการเปลี่ยนแปลงไปเงียบๆ โดยไม่บันทึกอะไรไว้ ทีมถัดไปจะตกอยู่ในสถานการณ์เดียวกับที่ทีมนี้เพิ่งเจอมาทุกประการ

ตามโมดูล 14 เรื่อง ADR (Architecture Decision Record) — การเปลี่ยนแปลงระดับนี้เข้าข่าย "one-way door" เพราะกระทบ deployment topology และพฤติกรรม runtime ทั้งระบบ จึงควรมี ADR เขียนไว้ <mark class="hl-insight">เป้าหมายของ ADR แรกนี้ไม่ใช่แค่บันทึกสิ่งที่เพิ่งค้นพบ แต่คือสร้างนิสัยให้ทุกการตัดสินใจถัดไปถูกบันทึกเป็นค่าเริ่มต้น ไม่ใช่ข้อยกเว้น</mark>

## คำถามเจาะลึกที่มักถูกถามต่อ

พออ่านเคสนี้จบ คนสัมภาษณ์หรือเพื่อนร่วมทีมมักไม่ถามแค่ว่า "ควรสำรวจระบบจริงไหม" (เนื้อเคสตอบไปแล้ว) แต่จะถามต่อว่า "สำรวจยังไงกันแน่ เชื่อผลที่ได้ได้แค่ไหน และทำยังไงไม่ให้กลับไปเป็นระบบไร้เอกสารอีก" สี่คำถามด้านล่างไล่ตั้งแต่การอ่านหลักฐานจากระบบจริงมาวาดเป็น diagram, การจัดข้อค้นพบเข้า view, การตรวจว่า diagram เป็นความจริง ไปจนถึงการเลือกและเขียน ADR แรก แต่ละข้อไล่ให้ครบว่าใช้ความรู้อะไร ข้างใต้ทำงานยังไง และพังได้ตรงไหน

### Q1: ไม่มีเอกสารเลย จะ "อ่านระบบที่รันอยู่" แล้ววาดเป็น C4 Container diagram ได้ยังไง หลักฐานแต่ละอย่างกลายเป็นกล่องหรือลูกศรอย่างไร

**ใช้ความรู้อะไร:** โมดูล 14 (C4 Model ระดับ Container คือหน่วยที่รันหรือ deploy แยกกันได้จริง เช่น แอป worker หรือ database — คำว่า container ตรงนี้ไม่ใช่ Docker) บวกโมดูล Reliability ของ System Design (หัวข้อ Observability เรื่อง log, metric, trace ที่เป็นที่มาของหลักฐานตอนระบบรันจริง)

**นึกภาพก่อน:** นักสืบที่เข้าห้องซึ่งไม่มีคำให้การของใครเลย มีแต่ร่องรอยหลายชนิด — สมุดนัดหมายที่บอกว่าใครต้องทำอะไรเมื่อไหร่ ประวัติการโทรที่บอกว่าใครคุยกับใคร และทะเบียนผู้พักอาศัยของตึกที่บอกว่ามีใครอยู่บ้าง ร่องรอยชนิดเดียวบอกภาพทั้งหมดไม่ได้ แต่ละชนิดตอบคำถามได้แค่ข้อเดียว นักสืบที่ดีจึงเอามาต่อกัน และถ้าร่องรอยสองอย่างขัดกันก็จดไว้ ไม่เลือกข้างเงียบๆ

**แก้ปัญหายังไง:** หลักคิดคือหลักฐานทุกชิ้นตอบได้แค่สองคำถาม — "มีอะไรรันอยู่" (กลายเป็น **กล่อง**) หรือ "ใครคุยกับใคร" (กลายเป็น **ลูกศร**) ตารางนี้สรุปแหล่งหลักฐานที่ไล่ดูได้ พร้อมจุดอ่อนของแต่ละอย่าง

| แหล่งหลักฐาน | ดูได้จาก | กลายเป็น | จุดอ่อนที่ต้องรู้ |
|---|---|---|---|
| Deployment config (docker-compose, systemd unit, Kubernetes manifest) | อ่านไฟล์ แล้วเทียบกับ process ที่รันจริง | กล่องของแต่ละ service และลูกศรจาก env var หรือ depends_on | บอกว่า "ตั้งใจให้รันอะไร" ไม่ใช่ "รันอะไรอยู่จริง" |
| crontab (cron คือตัวตั้งเวลารันงานของ Linux, crontab คือไฟล์ตารางงานของมัน) | ไล่ของทุก user, ไฟล์ใน `/etc/cron.d`, systemd timer ของทุกเครื่อง | กล่องของแต่ละ job และลูกศรตามที่สคริปต์เรียกไป | งานที่ตั้งบนเครื่องอื่นหรือ scheduler ในตัวแอปเองไม่โผล่ที่นี่ |
| Consumer ของ queue | หน้า management ของ broker หรือคำสั่ง `rabbitmqctl list_consumers` | ลูกศรจาก queue ไป consumer และเครื่องต้นทางของ connection บอกว่ากล่องนั้นอยู่ที่ไหน | เห็นเฉพาะ consumer ที่ต่ออยู่ตอนนั้น worker ที่รันเป็นช่วงๆ อาจไม่โผล่ |
| Connection ที่เปิดอยู่จริง | `ss -tnp` หรือ `lsof -i` บน server และ `SHOW PROCESSLIST` บนฝั่ง MySQL | ลูกศรจาก process ไปยัง host และ port ปลายทาง | เป็นภาพ ณ วินาทีนั้น connection สั้นๆ ของ cron job จะหลุด |
| Service discovery (เช่น Consul, Kubernetes Service) | ดูรายชื่อบริการที่ลงทะเบียนไว้ | รายชื่อกล่องที่ลงทะเบียนตัวเอง | ระบบเก่ามักไม่เคยลงทะเบียนอะไรเลย |
| APM (Application Performance Monitoring) และ distributed tracing | service map จากเครื่องมือ tracing | ลูกศรพร้อมความถี่จริงของการเรียก | เห็นเฉพาะโค้ดที่ติด instrumentation ระบบเก่าอาจไม่เคยถูกติดไว้ |
| Connection string ใน config หรือโค้ด | ไล่หา host, port, ชื่อ database | ลูกศรจากแอปไป database | อาจเป็นทางเก่าที่ไม่ถูกเรียกแล้ว ต้องยืนยันด้วย connection จริง |

จากตารางนี้ไล่เป็นขั้นตอนได้ดังนี้

1. **ทำรายชื่อกล่องจากหลายแหล่งที่เป็นอิสระต่อกัน** — deployment config, รายการ process บนแต่ละเครื่อง และ crontab แล้วรวมเป็นตารางเดียว กล่องที่ปรากฏในแหล่งเดียวแต่ไม่ปรากฏในแหล่งอื่นคือจุดที่ต้องสงสัยก่อน
2. **ลากลูกศรจากสิ่งที่ config บอก** — connection string และ env var ได้ "ลูกศรที่ตั้งใจให้มี" ซึ่งยังเป็นแค่สมมติฐาน
3. **ตรวจย้อนจากฝั่งปลายทาง** — ถาม database ว่าใครต่ออยู่ และถาม <mark class="hl-term">**message broker**</mark> (ตัวกลางที่ถือคิวข้อความ ในเคสนี้คือ RabbitMQ) ว่ามี consumer ตัวไหนสมัครดึงข้อความอยู่ วิธีนี้ไม่ต้องเชื่อโค้ดฝั่งต้นทางเลย และเป็นจุดที่ Undocumented Queue Consumer โผล่ขึ้นมา
4. **ใส่สิ่งที่ไม่มีเจ้าของลง diagram ไว้ก่อน** — กล่องหรือลูกศรที่พบจริงแต่ไม่มีใครรู้จัก ให้ติดป้ายว่า "ไม่ทราบเจ้าของ" แทนที่จะรอให้ครบก่อนแล้วค่อยวาด

**ข้างใต้ทำงานยังไง:** หลักฐานพวกนี้เชื่อถือได้เพราะแต่ละอย่างคือ **ข้อมูลที่ตัวระบบต้องใช้เองเพื่อทำงาน** ไม่ใช่เอกสารที่มีคนเขียนแยกไว้ ตัว cron ต้องอ่าน crontab เพื่อรู้ว่าจะสั่งรันอะไรเมื่อไหร่ ถ้าไฟล์ผิด job ก็ไม่รันตามที่ควร kernel ของระบบปฏิบัติการเก็บตารางของ TCP connection ที่เปิดอยู่ (`ss` และ `lsof` อ่านตารางนี้) ทุก connection ที่ established คือการคุยกันจริง และเลข port ปลายทางเป็นคำใบ้ชนิดบริการ (ค่าเริ่มต้นของ MySQL คือ 3306 ของ RabbitMQ คือ 5672 แต่เปลี่ยนได้ จึงเป็นแค่คำใบ้ ต้องยืนยันจากตัวบริการ) ส่วน broker ต้องรู้ว่ามี consumer ใครบ้างเพราะต้องรู้ว่าจะส่งข้อความให้ใคร รายชื่อ consumer จึงเป็นสมุดบัญชีภายในของ broker เอง และ database ก็เก็บรายการ connection ของทุกฝั่งที่ต่ออยู่เช่นกัน <mark class="hl-insight">หลักฐานที่ระบบใช้ทำงานจริงมีสถานะเป็น "ของที่กำลังถูกใช้" ถ้าผิดจะเห็นระบบพังหรือทำงานผิด ต่างจากเอกสารที่ผิดแล้วไม่มีอะไรเกิดขึ้นเลย</mark> นี่คือเหตุผลที่ควรเริ่มจากตรงนี้ ก่อนถามความจำของคน

**ถ้าพังหรือมีข้อควรระวังอะไร:**

- <mark class="hl-warning">ไฟล์ config บอกว่า "ตั้งใจให้รันอะไร" ไม่ใช่ "รันอะไรอยู่จริง"</mark> — docker-compose ที่ค้างอยู่ใน repo อาจเป็นของ environment เก่า และ connection string ที่ hardcode ในโค้ดอาจเป็นทางเก่าที่ไม่ถูกเรียกแล้ว ต้องเทียบกับ process และ connection จริงเสมอ
- **ภาพ ณ วินาทีเดียว** — connection ของ cron job เปิดแค่ไม่กี่วินาทีตอนเที่ยงคืน ถ้าไล่ดูตอนบ่ายจะไม่เห็นเลย ต้องอ่านเวลาจาก crontab แล้วไปดูตอนงานรันจริง หรือเก็บ log ของ connection ต่อเนื่อง
- **ช่องบอดของเครื่องมือ** — tracing เห็นเฉพาะโค้ดที่ติด instrumentation (ตัวเก็บข้อมูลที่ฝังในแอป) ระบบเก่าอย่าง PHP 5 ในเคสนี้อาจไม่เคยถูกติดไว้ และ scheduler ที่ฝังในตัวแอปเองก็ไม่โผล่ใน crontab
- **ทำแบบอ่านอย่างเดียวเสมอ** — เพราะระบบยังให้บริการผู้ใช้จริงอยู่ ขอสิทธิ์ read-only ก่อน คำสั่งดูรายชื่อ connection หรือ consumer ไม่กระทบระบบ แต่การเปิด debug logging หนักๆ บน production ต้องประเมินผลกระทบก่อนทุกครั้ง

### Q2: เจอ cron job ลึกลับหนึ่งตัวแล้ว จะเอาไปใส่ view ไหนของ 4+1 ทำไมไม่วาดรวมใน diagram เดียวให้จบ

**ใช้ความรู้อะไร:** โมดูล 14 (4+1 View Model — Logical ตอบเรื่องแนวคิดธุรกิจ, Process ตอบเรื่องการทำงานตอน runtime, Development ตอบเรื่องโครงสร้างซอร์สโค้ด, Physical ตอบเรื่องรันอยู่ที่ไหน และ +1 Scenarios คือการเดินเคสจริงผ่านทุก view เพื่อเช็คว่าสอดคล้องกัน) เนื้อเคสยกมาสาม view ตามข้อค้นพบที่เจอ แต่ Development View ก็มีข้อค้นพบให้ลงเหมือนกัน

**นึกภาพก่อน:** ข้อสังเกตเดียวตอนสำรวจบ้าน เช่น "มีท่อแก๊สเดินใต้ห้องครัว" ไม่ได้ลงพิมพ์เขียวแผ่นเดียว ช่างประปาอยากรู้ว่าท่ออยู่ตรงไหน คนทำครัวอยากรู้ว่าเปิดเตากับเครื่องดูดควันพร้อมกันได้ไหม ผู้ซื้อบ้านอยากรู้ว่าห้องนั้นใช้ทำอะไร ข้อสังเกตเดียวจึงต้องไปอยู่ในหลายแผ่น เพราะมันตอบหลายคำถาม ไม่ใช่เพราะมันซับซ้อน

**แก้ปัญหายังไง:** ใช้วิธี "ถามก่อนวาด" คือเอาข้อค้นพบหนึ่งข้อมาถามทีละ view ว่า view นี้อยากรู้อะไรเกี่ยวกับมัน ลองตามข้อค้นพบ Nightly Reconciliation Job ไปทีละ view

- **Physical:** รันบน VM ตัวไหน ตัวจัดตารางคืออะไร (cron ของระบบปฏิบัติการหรืออย่างอื่น) รันด้วย user ไหน และต่อไปที่ database ตัวไหน — ตอบได้จากเครื่องและ config จริง
- **Process:** รันทุกเที่ยงคืนพร้อมกับที่ queue consumer ประมวลผลอยู่ และทั้งคู่ต้องการ connection ของ database — ตอบได้จากการสังเกตตอนระบบรันจริงเท่านั้น เช่นกราฟจำนวน connection ตามเวลา
- **Logical:** "กระทบยอด" หมายถึงเทียบอะไรกับอะไร และสถานะแบบไหนถือว่าผิดปกติ — เป็นกฎธุรกิจที่ไม่เคยมีใครเขียนไว้ ต้องอ่านสคริปต์เพื่อรู้
- **Development:** สคริปต์อยู่ใน source control ไหม ใครแก้ล่าสุด ถ้าพบว่าวางอยู่บน server เพียงสำเนาเดียวโดยไม่มีใน git ให้ทำสำเนาเข้า repo ก่อนที่ใครจะแก้อะไร เพราะไม่เช่นนั้นระบบกำลังพึ่งโค้ดที่ไม่มีประวัติการแก้ไขเลย ซึ่งเป็นความเสี่ยงที่ต้องปิดก่อนเปลี่ยนอะไรใกล้ตัวมัน
- **+1 Scenarios:** เดินเคสเดียวตลอดสาย เช่น order ที่เปลี่ยนสถานะใกล้เที่ยงคืน แล้วถามว่า job กระทบยอดเห็นข้อมูลก่อนหรือหลังที่ consumer ประมวลผลเสร็จ ถ้าแต่ละ view เล่าเรื่องต่อกันไม่ได้ แปลว่ายังมีช่องว่าง

**ข้างใต้ทำงานยังไง:** แต่ละ view ใช้ **แหล่งความรู้คนละชนิด** และต้องเก็บหลักฐานคนละวิธี Physical มาจากไฟล์ config และเครื่องจริง Development มาจาก repo และ build Logical มาจากการอ่านโค้ดและ schema ของ database ส่วน Process ต้องสังเกตต่อเนื่องตามเวลาผ่าน metric, log หรือ trace ถ้ารวมเป็น diagram เดียว จะปนหลักฐานที่น่าเชื่อถือต่างระดับกันจนแยกไม่ออกว่าเส้นไหนเห็นจริงเส้นไหนเดา

ตัวอย่างชัดที่สุดคือ Process View ของเคสนี้ database มีเพดานจำนวน connection พร้อมกัน (เช่นค่า max connections ของ MySQL) และแอปมักใช้ <mark class="hl-term">**connection pool**</mark> คือกลุ่ม connection ที่เปิดค้างไว้ให้ request หยิบไปใช้ซ้ำ ถ้า job กับ consumer ยึด connection ไปเยอะพร้อมกัน ตอน monolith ขอ connection ใหม่ก็ต้องรอคิว request ปกติจึงช้าลง อาการนี้ไม่ปรากฏในโค้ดบรรทัดไหนเลย แต่เห็นได้จากกราฟ connection ที่พุ่งตรงเวลาเที่ยงคืน

**ถ้าพังหรือมีข้อควรระวังอะไร:**

- <mark class="hl-warning">อย่าเดาจากชื่อไฟล์</mark> — ไฟล์ชื่อ `reconcile.py` อาจทำอย่างอื่นเพิ่มด้วย ชื่อเป็นแค่เบาะแส Logical View ต้องมาจากการอ่านโค้ดจริง

- view ที่ตอบไม่ได้ให้ลงเป็นรายการ "ยังไม่รู้" อย่าปล่อยว่างหรือเดาเติม เพราะช่องว่างที่ถูกบันทึกไว้ตรงๆ ช่วยให้คนถัดไปรู้ว่าต้องระวังตรงไหน ต่างจากช่องว่างที่ไม่มีใครรู้ว่ามี

### Q3: จะรู้ได้ยังไงว่า diagram ที่ทีมวาดขึ้นใหม่ "เป็นความจริง" ไม่ใช่การเดาที่ดูน่าเชื่อ และวาดเสร็จแล้วจะกันไม่ให้หลุดอีกยังไง

**ใช้ความรู้อะไร:** โมดูล 14 หัวข้อ "ขั้นสูง: Documentation as Code กัน Diagram หลุดจาก Code จริง" (เก็บ diagram เป็น text ใน repo แล้วตรวจใน CI) บวกโมดูล 21 (Architecture Erosion และ Fitness Function — ระบบเสื่อมทีละจุดโดยไม่มีใครตั้งใจ และตรวจอัตโนมัติได้)

**ปัญหาคืออะไร:** diagram ที่วาดจากการสำรวจเสี่ยงสองแบบ แบบแรกคือ "ผิดตั้งแต่วันแรก" เพราะเชื่อ config เก่าหรือคำบอกเล่าที่จำคลาดเคลื่อน แบบที่สองคือ "ถูกวันนี้ แต่ล้าสมัยพรุ่งนี้" เมื่อใครสักคนแก้ระบบ ทั้งสองแบบอันตรายเพราะ diagram ที่ผิดแต่ดูน่าเชื่อ ทำให้คนตัดสินใจพลาดอย่างมั่นใจ ซึ่งแย่กว่าไม่มีเอกสารเลย (ตามที่หัวข้อขั้นสูงเรื่อง Documentation as Code ชี้ไว้) และในเคสนี้ diagram ชุดใหม่คือเอกสารเดียวที่ระบบมี

**แก้ปัญหายังไง:** สี่อย่างที่ทำร่วมกัน

1. **ตรวจสองทาง** — ทิศแรกจาก diagram ไปหาของจริง: ทุกกล่องและลูกศรต้องชี้หลักฐานที่ตรวจซ้ำได้ (คำสั่ง ไฟล์ วันที่ตรวจ) ทิศที่สองจากของจริงกลับมาที่ diagram: เอา connection, process และ consumer ที่สังเกตได้จริงในช่วงเวลาหนึ่งมาเทียบว่ามีตัวไหนที่ diagram ไม่มี
2. **ยืนยันเจตนากับคนแบบชี้ของจริง** — ระบบบอก "อะไร" แต่ไม่บอก "ทำไม" (ตามตารางในเนื้อเคส) จึงเอาสิ่งที่พบไปถามคนที่กำลังจะย้ายทีมว่า "consumer ตัวนี้ต่อมาจากเครื่องนี้ คุณรู้ไหมว่าทำไม" ไม่ใช่ถามลอยๆ ว่า "ระบบมีอะไรบ้าง" เพราะคนนึกออกเมื่อเห็นของตรงหน้าง่ายกว่านึกเองจากศูนย์มาก
3. **ติดป้าย** <mark class="hl-term">**ระดับความมั่นใจ (confidence level)**</mark> ให้ทุกกล่องและลูกศร เช่นสามระดับ Observed (เห็นจากระบบจริง ระบุวันที่ตรวจ) Inferred (อนุมานจากโค้ดหรือ config) และ Unverified (ได้ยินมาจากคน ยังไม่ยืนยัน) เป็นข้อตกลงของทีมเอง ไม่ใช่มาตรฐานของ C4 แสดงด้วยเส้นทึบกับเส้นประ
4. **กันหลุดหลังวาดเสร็จ** — เก็บ diagram เป็น text ใน repo ตามหัวข้อขั้นสูง และเก็บ "สคริปต์สำรวจ" (คำสั่งที่ใช้ไล่ดู consumer, connection, crontab) ไว้ใน repo เดียวกัน เพื่อรันซ้ำเป็นระยะแล้วเทียบผลกับ diagram

- **การสแกนซ้ำที่ไม่มีเจ้าของจะถูกเลิกทำเงียบๆ** — ต้องกำหนดคนรับผิดชอบและรอบเวลาชัดเจน และเขียนเป็นสคริปต์ที่รันได้โดยไม่ต้องจำขั้นตอน

### Q4: ทำไม ADR แรกของเคสนี้เลือกเรื่อง "แยก consumer" และอะไรทำให้นับเป็น one-way door ทั้งที่ deploy กลับไปที่เดิมได้ อีกทั้งเขียนยังไงให้ทีมเขียน ADR ต่อเป็นนิสัย

**ใช้ความรู้อะไร:** โมดูล 14 (ADR ฟอร์แมต Michael Nygard 5 ส่วน และเกณฑ์ one-way door กับ two-way door) บวกโมดูล Async & Messaging ของ System Design (หัวข้อ Message Queue เรื่องการ acknowledge ข้อความ)

**นึกภาพก่อน:** ย้ายตู้ไปรษณีย์หน้าบ้านไปอีกมุมหนึ่ง ย้ายกลับได้เสมอ แต่ถ้าระหว่างที่ตู้อยู่มุมใหม่ มีคนรับจดหมายไปเปิดอ่านและฉีกทิ้งแล้ว จดหมายฉบับนั้นเอากลับมาไม่ได้ "การย้าย" ย้อนได้ แต่ "ผลข้างเคียงระหว่างทาง" ย้อนไม่ได้ และนี่คือจุดที่ตัดสินว่าเรื่องไหนคือ one-way door

**แก้ปัญหายังไง:** เกณฑ์ที่ใช้ตัดสินไม่ใช่ถามว่า "ย้อน action ได้ไหม" แต่ถามสองข้อ ข้อแรก ย้อนกลับได้ภายในไม่กี่ชั่วโมงโดยไม่มีผลข้างเคียงค้างอยู่ไหม ข้อสอง กระทบหลาย service หรือหลายทีมไหม (ตามตารางในโมดูล 14) ถ้าย้อนไม่ได้หรือกระทบกว้าง ให้เขียน ADR ส่วนเรื่องที่ย้อนง่ายและแคบ จดสั้นๆ ใน PR ก็พอ

ส่วน ADR แรกควรเลือกเรื่องที่ผ่านสามข้อพร้อมกัน คือ (1) เป็นการตัดสินใจที่ทีมกำลังลงมือทำจริง ไม่ใช่ทุกอย่างที่เพิ่งค้นพบ (การบันทึกสิ่งที่ค้นพบเป็นหน้าที่ของ diagram) (2) ผ่านเกณฑ์ one-way door (3) เป็นเรื่องที่โค้ดอธิบาย "ทำไม" ไม่ได้ การย้าย consumer ตรงทั้งสามข้อ จากนั้นเขียนตามลำดับนี้

1. **Context** — เขียนสิ่งที่พบ พร้อมชี้ว่ารู้ได้ยังไง (ลิงก์ไปที่กล่องที่ติดป้าย Observed ใน diagram) และเขียนตรงๆ ว่า "ไม่ทราบเหตุผลเดิมของการทำแบบนี้" ช่องว่างที่ยอมรับตรงๆ เป็นข้อมูลที่มีค่า เพราะบอกคนถัดไปว่าควรระวังตรงไหน
2. **Decision** — ประโยคสั้นที่ชัด พร้อมแผน cutover (ขั้นตอนสลับจากตัวเก่าไปตัวใหม่) ว่าทำยังไงไม่ให้ข้อความหาย
3. **Consequences** — ทั้งข้อดี ต้นทุน และ "ย้อนกลับได้แค่ไหน" ตามรูปแบบ Nygard
4. **ส่งใน PR เดียวกับการเปลี่ยนจริง** แล้วรีวิวเหมือนโค้ด ตามที่โมดูล 14 สอน
5. **ลดแรงเสียดทานเพื่อให้ติดเป็นนิสัย** — template ไฟล์เดียวใน repo, ADR ยาวไม่เกินครึ่งหน้า, ใส่กฎ "one-way door ต้องมี ADR" ไว้ใน Decision ของ ADR-001 เอง (ตามที่เคสนี้ทำ) และเพิ่มช่องติ๊กใน template ของ PR ว่า "เปลี่ยนโครงสร้างหรือไม่ ถ้าใช่ ลิงก์ ADR"

**ถ้าพังหรือมีข้อควรระวังอะไร:**

- <mark class="hl-warning">บังคับเขียน ADR ทุกเรื่อง ทีมจะเบื่อและเลิกเขียน</mark> (โมดูล 14 เตือนไว้เหมือนกัน) ใช้เกณฑ์สองข้อข้างบนคัดเรื่อง และจดเรื่อง two-way door สั้นๆ ใน PR
- **ตัดสินผิดทิศเพราะท่องว่า "แยก service คือ one-way"** — ถ้า consumer ตัวนี้ไม่มีผลข้างเคียงถาวร (เช่นประมวลผลซ้ำได้ปลอดภัยตามหลัก Idempotency ในโมดูล Reliability ของ System Design) การย้ายอาจเป็น two-way door เกณฑ์ต้องดูจากข้อเท็จจริงของระบบนั้น ไม่ใช่ท่องจำ และในเคสนี้ที่ไม่มีใครรู้ว่า consumer ทำอะไร ควรถือว่ามีผลข้างเคียงไว้ก่อนจนกว่าจะพิสูจน์ได้ว่าไม่มี
- **ADR ที่เขียนหลังเปลี่ยนไปแล้วมักกลายเป็นข้อแก้ตัว** — เขียนก่อนหรือพร้อมลงมือ และเมื่อบริบทเปลี่ยนก็เขียน ADR ใหม่แล้วมาร์กอันเก่าเป็น Superseded ไม่ลบทิ้ง
- **ADR-001 ที่ยาวเป็นหลายหน้าและไม่มีใครรีวิว** จะกลายเป็นเอกสารที่ไม่มีใครเชื่อ เหมือน diagram ที่ไม่มีใครดูแลในเคสนี้

## ADR ตัวอย่าง

> **Title:** ADR-001: แยก Undocumented Queue Consumer ออกเป็น Container อิสระ พร้อมเริ่มบันทึกเอกสารสถาปัตยกรรมของระบบ
> **Status:** Accepted
> **Context:** ระบบ Legacy Order Platform ไม่มีเอกสารสถาปัตยกรรมหลงเหลืออยู่เลยตอนทีมใหม่เข้ารับช่วง ทีมสำรวจ infra จริงจนพบว่ามี Node.js worker ที่ดึงข้อความจาก queue เดิมอยู่ รันอยู่บน VM เดียวกับ Order Monolith และถูก deploy พ่วงไปพร้อมกันทุกครั้ง โดยไม่มีใครในทีมเดิมจำได้ว่าใครเป็นคนเขียนขึ้นมา ทำให้ deploy monolith ทุกครั้งเสี่ยงกระทบ consumer ตัวนี้โดยไม่ตั้งใจ
> **Decision:** แยก queue consumer ออกมาเป็น container อิสระ deploy แยกจาก monolith และเริ่มเก็บ C4 Container diagram กับ 4+1 View ที่สร้างจากการสำรวจครั้งนี้ไว้ใน repo คู่กับโค้ด พร้อมกำหนดว่าการเปลี่ยนแปลงระดับ one-way door ทุกครั้งนับจากนี้ต้องมี ADR กำกับ
> **Consequences:** Deploy ของ monolith และ consumer แยกอิสระจากกัน ลดความเสี่ยงจากการกระทบกันโดยไม่ตั้งใจ ทีมต้องเสียเวลาช่วงแรกเขียนเอกสารที่ไม่เคยมีมาก่อน แต่แลกกับการที่ทีมถัดไปจะไม่ต้องเริ่มจากศูนย์เหมือนที่ทีมนี้เพิ่งเจอมา
